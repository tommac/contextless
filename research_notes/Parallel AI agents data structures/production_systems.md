# Production parallel-agent systems (2024 to late 2026): architecture, artifacts, isolation, merge, costs, and the arguments against

Research date: 2026-11-17. Documentation pages are cited as they read on that date; blog posts carry their own publication dates. Pages were read through a fetch tool that summarizes, so short quoted phrases are as returned by that tool and long passages are paraphrase. Where only search-result snippets were available this is flagged as "secondary, not verified against the primary".

Labels used below: **[MEASURED]** = a number the vendor or author reports from their own run or eval; **[CLAIM]** = vendor assertion without a number or method; **[ANECDOTE]** = single practitioner practice or opinion; **[DOCS]** = product documentation describing a mechanism.

## 1. Anthropic's multi-agent research system (orchestrator-worker, briefs, artifacts, token multiple, gain, synchronous limits)

### Takeaway
Anthropic's Research feature (post dated 2025-06-13) is a lead agent that plans, spawns 3 to 5 subagents in parallel with explicit briefs, receives condensed findings, and hands the result to a separate citation pass; it reported a 90.2% gain over single-agent Opus 4 on an internal research eval at roughly 15x the tokens of a chat. The same post says the lead waits synchronously for each batch of subagents and that most coding tasks are a poor fit.

### Cited Findings
- **Date and authors.** Published 2025-06-13 by Jeremy Hadfield, Barry Zhang, Kenneth Lien, Florian Scholz, Jeremy Fox, Daniel Ford. — [Anthropic, "How we built our multi-agent research system"](https://www.anthropic.com/engineering/multi-agent-research-system)
- **Architecture.** "a multi-agent architecture with an orchestrator-worker pattern": a lead agent (LeadResearcher) delegates to subagents that run in parallel; after the research loop ends a separate CitationAgent processes the documents and the report to "identify specific locations for citations". — [Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system)
- **The brief (data structure passed down).** Each subagent needs an objective, an output format, guidance on which tools and sources to use, and clear task boundaries. Early short instructions such as "research the semiconductor shortage" produced duplicated work and misread tasks. — [Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system)
- **What comes back up.** Subagents act as filters: they search, then return condensed findings to the lead (example in the post: "returning a list of companies to the lead agent"). — [Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system)
- **Artifacts bypass the lead.** Subagents can store their work in external systems and "pass lightweight references back to the coordinator", which the post says reduces information loss and token overhead compared with copying everything through the lead's context. — [Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system)
- **Plan persistence.** The lead saves its plan to memory because "if the context window exceeds 200,000 tokens it will be truncated"; agents summarize completed phases and spawn fresh subagents with clean contexts while keeping continuity. — [Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system)
- **[MEASURED] Gain.** A Claude Opus 4 lead with Claude Sonnet 4 subagents "outperformed single-agent Claude Opus 4 by 90.2%" on Anthropic's internal research eval. (Internal eval; the task set is not published.) — [Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system)
- **[MEASURED] Token cost.** Agents use "about 4x more tokens than chat interactions"; multi-agent systems use about 15x more than chats. — [Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system)
- **[MEASURED] Why it works.** On BrowseComp, token usage alone explained 80% of performance variance; token usage, number of tool calls and model choice together explained 95%. — [Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system)
- **[MEASURED] Speed.** The lead spins up 3 to 5 subagents in parallel and subagents call 3+ tools in parallel; together these "cut research time by up to 90% for complex queries". — [Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system)
- **Effort-scaling rules embedded in the prompt.** Simple fact-finding: 1 agent, 3 to 10 tool calls. Direct comparisons: 2 to 4 subagents, 10 to 15 calls each. Complex research: more than 10 subagents with divided responsibilities. — [Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system)
- **Synchronous execution limit.** The lead waits for each set of subagents to finish, so it cannot steer them mid-run, subagents cannot coordinate with each other, and "the entire system can be blocked while waiting for a single subagent to finish searching". — [Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system)
- **Stated poor fits.** Domains that require "all agents to share the same context" or have many inter-agent dependencies; most coding tasks, which have fewer truly parallelizable parts than research. — [Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system)
- **Operations.** Evaluation began with about 20 real-usage queries; an LLM judge with a single prompt scoring 0.0 to 1.0 plus pass/fail aligned best with humans; human testing caught failures automation missed (preference for SEO content farms). State is judged by end state, not by the path. Errors are handled by resuming "from where the agent was when the errors occurred" using checkpoints and retries. Deploys use rainbow deployments so running agents are not broken mid-task. — [Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system)
- **Outside reading of the same post.** Harrison Chase (LangChain, 2025-06-16) points out that Anthropic parallelizes only the reading phase; a single agent writes the final report in one call. — [LangChain, "How and when to build multi-agent systems"](https://www.langchain.com/blog/how-and-when-to-build-multi-agent-systems)

### Inferences
- The system's three data structures are: a brief (objective, output format, tool/source guidance, boundaries), a condensed return message, and an out-of-band artifact store addressed by reference. The merge step is not a merge of writes: it is a single writer (lead) plus a post-hoc citation pass.
- The 90.2% figure and the 15x figure are from different measurements (an internal eval and a usage comparison), so they should not be combined into a "gain per token" number.
- The 80% variance result implies much of the benefit is extra token budget spread across separate context windows, not coordination as such.

### Gaps
- The internal eval's task set, size and scoring rubric are not published, so the 90.2% number cannot be reproduced.
- The post does not specify the artifact store's format or how references are resolved.
- I did not find a later Anthropic post revising these numbers or announcing asynchronous subagent execution for the Research product itself.

## 2. Coding-agent products: Claude Code, Codex, Cursor, Devin/Cognition, Jules, Copilot, others

### Takeaway
By late 2026 every major coding agent ships some form of parallelism, and they converge on the same shape: a coordinator hands self-contained briefs to workers in separate context windows and separate checkouts (worktree, VM or repo copy), and workers return a summary or a branch/PR. The vendors that tried peer-to-peer coordination with shared mutable state (Cursor) report that it failed; the loudest critic (Cognition) moved in April 2026 from "don't build multi-agents" to "multi-agent works when writes stay single-threaded".

### Cited Findings

#### Claude Code (docs as of 2026-11-17)
- **[DOCS] Five surfaces.** Subagents, agent view (background sessions), agent teams (experimental), dynamic workflows (a script that runs many subagents and cross-checks results), and projects (cloud threads). Worktrees, cross-session messaging and `/batch` are listed as supporting tools. — [Claude Code docs, "Run agents in parallel"](https://code.claude.com/docs/en/agents)
- **[DOCS] Subagent brief and return.** A non-fork subagent "doesn't see your conversation history, the skills you've already invoked, or the files Claude has already read. Claude composes a delegation message that summarizes the task". It starts with its own system prompt, the task message, CLAUDE.md files and a git status snapshot. It returns a summary to the caller. A fork instead inherits the full parent conversation. — [Claude Code docs, subagents](https://code.claude.com/docs/en/sub-agents)
- **[DOCS] Limits.** Subagents can nest "up to three layers below the main conversation"; by default spawning fails at 20 concurrently running subagents ("Concurrent subagent limit reached"). — [Claude Code docs, subagents](https://code.claude.com/docs/en/sub-agents)
- **[DOCS] Context cost warning.** "Running many subagents that each return detailed results can consume significant context, and each subagent spends tokens of its own while it runs." — [Claude Code docs, subagents](https://code.claude.com/docs/en/sub-agents)
- **[DOCS] Agent teams data structures.** Team lead, teammates, shared task list, mailbox. Each mailbox is a JSON file at `~/.claude/teams/{team-name}/inboxes/{agent-name}.json`; team config at `~/.claude/teams/{team-name}/config.json` (a `members` array with name and agent ID); task list under `~/.claude/tasks/{team-name}/`. Tasks have three states (pending, in progress, completed) plus dependencies; a dependent task shows as blocked and is unblocked automatically when its prerequisites complete. "Task claiming uses file locking to prevent race conditions". — [Claude Code docs, agent teams](https://code.claude.com/docs/en/agent-teams)
- **[DOCS] Agent teams context.** A teammate gets project context plus the lead's spawn prompt; "The lead's conversation history does not carry over." Teammates message each other directly; idle notifications carry the teammate's final answer to the lead. — [Claude Code docs, agent teams](https://code.claude.com/docs/en/agent-teams)
- **[DOCS] Agent teams status and limits.** Experimental, off by default (`CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1`). Known limits: task status can lag because teammates fail to mark tasks complete, no nested teams, one team per session, no restore of in-process teammates on resume, the lead sometimes declares the team done early or does the work itself. — [Claude Code docs, agent teams](https://code.claude.com/docs/en/agent-teams)
- **[DOCS] Teams do not isolate files.** "Agent teams don't isolate teammates in worktrees, so partition the work so each teammate owns a different set of files." "Two teammates editing the same file leads to overwrites." — [Run agents in parallel](https://code.claude.com/docs/en/agents); [agent teams](https://code.claude.com/docs/en/agent-teams)
- **[DOCS] Quality gates.** Hooks `TeammateIdle`, `TaskCreated`, `TaskCompleted`; exit code 2 rejects the transition and sends feedback. — [Claude Code docs, agent teams](https://code.claude.com/docs/en/agent-teams)
- **[DOCS] `/batch`.** A skill that "has Claude split one large change into 5 to 30 worktree-isolated subagents"; outside git each subagent publishes with the project's VCS commands and, if it cannot open a pull request, reports what it published. — [Run agents in parallel](https://code.claude.com/docs/en/agents); [worktrees](https://code.claude.com/docs/en/worktrees)
- **[DOCS] Dynamic workflows.** Positioned for "a codebase-wide audit, a 500-file migration, cross-checked research, or a plan drafted from several angles", where "a script holds the plan instead of Claude's turn-by-turn judgment". — [Run agents in parallel](https://code.claude.com/docs/en/agents)

#### OpenAI Codex (docs as of 2026-11-17; the developers.openai.com Codex pages redirect to learn.chatgpt.com)
- **[DOCS] Subagents.** Codex runs specialized agents in parallel and combines results into one response; enabled by default in current local releases. Spawning is by explicit request ("spawn two agents", "use one agent per point") or by AGENTS.md/skill instruction. Subagents return summaries rather than raw intermediate output; Codex waits for all requested results and returns a consolidated response. Built-in agents: `default`, `worker`, `explorer`; custom agents are one file each under `~/.codex/agents/` or `.codex/agents/` with required `name`, `description`, `developer_instructions`. Concurrency cap: `agents.max_concurrent_threads_per_session` (`agents.max_threads` is a legacy alias); no default number is stated. Subagents inherit the parent's sandbox and approval settings, and "instructions asking an agent not to edit don't create a read-only sandbox". — [Codex docs, subagents](https://learn.chatgpt.com/docs/agent-configuration/subagents)
- **[DOCS] Codex guidance on fit.** Parallel agents are recommended for read-heavy work (exploration, tests, triage, summarization); write-heavy parallel workflows should be used with care because agents editing code simultaneously can conflict and add coordination overhead; subagent workflows consume more tokens than single-agent runs. — [Codex docs, subagents](https://learn.chatgpt.com/docs/agent-configuration/subagents)
- **[DOCS] Codex worktrees.** Managed worktrees live in `$CODEX_HOME/worktrees`, start from the HEAD of the selected branch (uncommitted changes are applied too) and stay in detached HEAD so several can exist without creating branches. Default retention is the 15 most recent managed worktrees, with a snapshot saved before deletion. "Handoff" moves a chat and its code between the Local checkout and a worktree. There is no automatic merge: the user chooses "Create branch here", commits, pushes and opens a PR. Scheduled tasks run on dedicated background worktrees. — [Codex docs, git worktrees](https://learn.chatgpt.com/docs/environments/git-worktrees)

#### Cursor
- **[DOCS] Local parallel agents.** Each agent gets an isolated git checkout: "Use worktrees when you want to start several agents on the same repo without conflicts." Commands: `/worktree`, `/best-of-n`, `/apply-worktree`, `/delete-worktree`. "`/best-of-n` compares runs only. It does not merge changes back into your main checkout for you." Per-worktree setup is declared in `.cursor/worktrees.json`. Default cap of 25 worktrees per machine (`cursor.worktreeMaxCount`, Cursor 3.5+). The page does not say how conflicts are handled on apply. — [Cursor docs, worktrees](https://cursor.com/docs/configuration/worktrees)
- **Secondary, not verified against the primary:** Cursor 2.0 (October 2025) allowed up to eight parallel agents, each in a worktree or remote sandbox. — [Cursor forum, "Cursor 3: Worktrees & Best-of-N"](https://forum.cursor.com/t/cursor-3-worktrees-best-of-n/156507) (search-result summary of several third-party posts)
- **Many agents on one codebase, first account (2026-01-14, Wilson Lin).**
  - Attempt 1, flat peers with a shared coordination file and a lock: agents "would hold locks for too long, or forget to release them entirely"; twenty agents slowed to the effective throughput of two or three; agents could crash while holding locks, re-acquire locks they held, or edit the file without locking. **[MEASURED, informal]**
  - Attempt 2, optimistic concurrency (free reads, a write fails if state changed since last read): simpler and more robust, but without hierarchy agents became risk-averse, avoided hard tasks and made small safe changes; work churned without progress.
  - Attempt 3, roles: planners continuously explore and create tasks and can spawn sub-planners; workers take one task, do not coordinate with other workers, and push when done; a judge decides at the end of each cycle whether to continue, and the next iteration starts fresh.
  - An integrator role for quality control and conflict resolution "created more bottlenecks than it solved" and was removed; workers handled conflicts themselves.
  - **[MEASURED]** Web browser from scratch: close to a week, over 1 million lines across 1,000 files. Solid to React migration of Cursor's own codebase: over three weeks, +266K/-193K, passing CI but "still needs careful review". Java LSP: 7.4K commits, 550K LoC. Windows 7 emulator: 14.6K commits, 1.2M LoC. Excel clone: 12K commits, 1.6M LoC. "Trillions of tokens" across hundreds of concurrent agents. (Lines and commits are volume measures, not quality measures.)
  - Model per role: GPT-5.2 held up better on long autonomous work than Opus 4.5, which tended to stop early; GPT-5.2 planned better than GPT-5.1-Codex.
  - Lessons: removing complexity helped more than adding it; prompts mattered more than harness; periodic fresh starts are still needed against drift. — [Cursor, "Scaling long-running autonomous coding"](https://cursor.com/blog/scaling-agents)
- **Second account, revised design (2026-02-05, Wilson Lin).** This post revises the January description and should be preferred:
  - Lock failure restated as "20 agents would slow to the throughput of 1-3".
  - The planner/executor/workers/judge design was "bottlenecked by the slowest worker". The independent planner was then merged into a continuous executor and "the judge was removed to keep the system simple"; the overloaded executor then misbehaved (slept, stopped running agents, did work itself, refused to plan, failed to merge worker changes, claimed premature completion).
  - Final design: a root planner that "does no coding itself"; recursive sub-planners that each own a narrow slice; workers that are "unaware of the larger system", "work on their own copy of the repo", and at the end "write up a single handoff that the system submits to the planner" containing "important notes, concerns, deviations, findings, thoughts, and feedback". The planner receives the handoff as a follow-up message and may plan further.
  - The integrator was removed because it became "an obvious bottleneck" with hundreds of workers passing through one gate.
  - Merge policy: requiring 100% correctness before every commit serialized the system and caused pile-ons on the same breakage, so the team accepted a small, steady error rate and occasional overlapping edits that "settle" over time. A periodically snapshotted and fixed-up "green" branch is proposed but not demonstrated.
  - **[MEASURED]** Peak "~1,000 commits per hour across 10M tool calls over a period of one week"; most runs peaked at several hundred agents on one large machine, where disk I/O from concurrent builds became the bottleneck.
  - Instruction lessons: "Agents have immense engineering skill but will follow instructions to the end, good or bad"; numeric ranges ("Generate 20-100 tasks") beat vague quantities; "No TODOs, no partial implementations" beat softer wording. — [Cursor, "Towards self-driving codebases"](https://cursor.com/blog/self-driving-codebases)
- **[CLAIM]** Cursor's long-running agents research preview (February 2026) is described as producing larger PRs with comparable merge rates; I saw this only as a search-result caption. — [Cursor, "Long-running agents"](https://cursor.com/blog/long-running-agents) (secondary, not verified against the primary)

#### Cognition / Devin
- **2025-06-12, Walden Yan, "Don't Build Multi-Agents".** Principle 1: "Share context, and share full agent traces, not just individual messages". Principle 2: "Actions carry implicit decisions, and conflicting decisions carry bad results". Example: a Flappy Bird clone split in two, where one subagent built a Super Mario style background and the other a bird that did not match; copying the original task to both does not fix it because later turns and tool calls also shape interpretation. Recommendation: "just use a single-threaded linear agent", adding for long tasks a separate model "whose key purpose is to compress a history of actions & conversation into key details" (described as hard to get right; Cognition fine-tuned a smaller model for it). On Claude Code at that time: it "never does work in parallel with the subtask agent" and the subagent is "usually only tasked with answering a question, not writing any code". Verdict: "in 2025, running multiple agents in collaboration only results in fragile systems". — [Cognition, "Don't Build Multi-Agents"](https://cognition.com/blog/dont-build-multi-agents)
- **Revision, 2026-03-19, product.** "Devin can now manage Devins": a coordinator session scopes the work, assigns each piece to a managed Devin, monitors progress, resolves conflicts and compiles results. Each managed Devin is "a full Devin, running in its own isolated virtual machine". The coordinator can message children mid-task, pause or terminate them, and reads children's full trajectories. Suggested uses: QA one page per child, large migrations, security and dependency audits per service ("no more than 10 running at a time"), class-to-hooks refactors batched into PRs, end-to-end tests for 10 recently touched features. No performance numbers. — [Cognition, "Devin can now manage Devins"](https://old.cognition.ai/blog/devin-can-now-manage-devins)
- **Revision, 2026-04-22, Walden Yan, "Multi-Agents: What's Actually Working".** "Our original observations still hold today for parallel-writer swarms." What works is "setups where multiple agents contribute intelligence to a task while writes stay single-threaded". Three patterns:
  1. Generator-verifier. **[MEASURED]** Devin Review catches an average of 2 bugs per PR, about 58% of them severe. The reviewer deliberately gets no shared context and looks only at the diff; the coding agent, which holds the user's instructions, filters the reviewer's findings to avoid loops and out-of-scope work.
  2. "Smart friend": a primary model calls a stronger model as a tool; sharing a fork of the full context is a reasonable "80/20 solution"; in production Claude plus GPT acted as "a capability router rather than a difficulty escalator".
  3. Manager with children (map-reduce-and-manage): a manager Devin splits the task, spawns children, coordinates through an internal MCP, then synthesizes. Failures observed: managers became overly prescriptive without deep codebase context; agents assumed they shared state with children when they did not; cross-agent communication "doesn't happen by default".
  Unstructured swarms are "mostly a distraction". "The open problems are all communication problems", including how a child surfaces a discovery that should change its siblings' work. — [Cognition, "Multi-Agents: What's Actually Working"](https://cognition.com/blog/multi-agents-working)

#### GitHub Copilot coding agent
- **2025-12-01, Matt Nigh, GitHub.** Mission control is a single interface for assigning and tracking coding-agent tasks; results arrive as pull requests. Review order recommended: session logs (reasoning), files changed (unexpected files, shared code paths), checks ("When checks fail, don't just restart the agent. Investigate why."). Parallel agents in one repo can conflict when they touch the same files: "Be thoughtful about partitioning work." — [GitHub Blog, "How to orchestrate agents using mission control"](https://github.blog/ai-and-ml/github-copilot/how-to-orchestrate-agents-using-mission-control/)
- **Secondary, not verified against GitHub Docs:** each task produces a draft pull request the agent pushes commits to, and the agent never merges on its own. — [GitHub Blog, agents panel announcement](https://github.blog/news-insights/product-news/agents-panel-launch-copilot-coding-agent-tasks-anywhere-on-github/) (search-result summary)

#### Google Jules
- **Secondary only, not verified against Google's documentation:** each task runs in a fresh short-lived cloud VM with a cloned repo and ends in a pull request; concurrency is capped by plan (3 concurrent tasks free, 15 on Pro, 60 on Ultra, as third-party sites reported in 2026). — [danilchenko.dev Jules review](https://www.danilchenko.dev/posts/google-jules-review/); [Activepieces pricing summary](https://www.activepieces.com/blog/google-jules-pricing-free-pro-and-ultra-plans-2026) (search-result summaries)

### Inferences
- Three coordination topologies are in production: (a) hub-and-spoke with summary return (Claude Code subagents, Codex subagents, Anthropic Research, Devin manager); (b) shared task list plus mailboxes with claim locks (Claude Code agent teams, still experimental); (c) recursive planner tree with one-way handoff documents (Cursor's research harness). Independent "fire off N tasks, get N PRs" products (Copilot coding agent, Jules, Codex worktree chats, Cursor best-of-n) have no inter-agent coordination at all; the human is the integrator.
- Cursor and Cognition independently report the same failure: peers sharing mutable coordination state (lock file, assumed shared state) do worse than strict hierarchy with explicit one-way messages.
- Cognition's position changed in scope, not in principle. The 2025 objection (conflicting implicit decisions) is retained for parallel writers; what was added is read-side or advisory parallelism and a manager pattern for separable work. A report should not cite the 2025 essay as Cognition's current view without the April 2026 qualifier.
- Cursor's January 2026 post (planner/worker/judge) is superseded by its February 2026 post (judge and standalone integrator removed, recursive planners, handoff documents).

### Gaps
- Amp/Sourcegraph and Factory: not researched within the call budget; no findings.
- OpenAI Codex cloud tasks (the hosted, one-container-per-task product) were not read from a primary source; only the local worktree and subagent docs were.
- Claude Code's dynamic workflows page itself was not read; only the comparison page that describes it.
- Google Jules and the Copilot coding agent branch/PR mechanics rest on secondary summaries.
- No vendor publishes a controlled comparison of N parallel coding agents against one agent on the same tasks with a quality metric. Cursor's numbers are volume (lines, commits/hour); Cognition's are bugs caught by review.

## 3. How coding-agent systems avoid or resolve conflicting edits

### Takeaway
The dominant mechanism is physical isolation before the fact (one worktree, VM or repo copy per agent) plus partitioning by file ownership; almost no product performs an automated semantic merge. Integration is done by a human through PRs, by the coordinator agent, or, in Cursor's research harness, by letting workers push to a shared branch and tolerating a small error rate because a single integrator gate became the bottleneck.

### Cited Findings
- **One worktree per agent (Claude Code).** `claude --worktree <name>` creates `.claude/worktrees/<name>/` on a new branch `worktree-<name>`, branching by default from the remote default branch (`worktree.baseRef: "fresh"`; `"head"` branches from local HEAD). Subagents get the same via `isolation: worktree`. A subagent worktree with no changes is removed automatically; one with changes stays until a periodic sweep can remove it without losing work. Claude Code holds a `git worktree lock` while an agent runs. — [Claude Code docs, worktrees](https://code.claude.com/docs/en/worktrees)
- **Enforcement, not convention (Claude Code).** While isolated, edits targeting the main checkout are blocked, as are commands whose working directory resolves to the main checkout and git redirects (`git -C`, `--git-dir`, `GIT_DIR`, `GIT_WORK_TREE`). The checks do not track arbitrary shell writes such as `cp` into the main checkout. — [Claude Code docs, worktrees](https://code.claude.com/docs/en/worktrees)
- **Shared state that worktrees do not isolate.** All worktrees write to the same `.git` directory; permission approvals saved in one worktree apply to all. — [Claude Code docs, worktrees](https://code.claude.com/docs/en/worktrees)
- **File ownership instead of isolation (Claude Code agent teams).** Teammates share one working directory; the documented remedy is to "Break the work so each teammate owns a different set of files." — [Claude Code docs, agent teams](https://code.claude.com/docs/en/agent-teams)
- **Claims and locks on tasks, not files (Claude Code agent teams).** Task claiming uses file locking; tasks with unmet dependencies cannot be self-claimed. — [Claude Code docs, agent teams](https://code.claude.com/docs/en/agent-teams)
- **Detached-HEAD worktrees, manual merge (Codex).** Worktrees are detached so they do not create branches; Git refuses to check out one branch in two worktrees; there is no automatic merge, only Handoff into Local or "Create branch here" followed by a PR. — [Codex docs, git worktrees](https://learn.chatgpt.com/docs/environments/git-worktrees)
- **Compare, then apply one (Cursor).** `/best-of-n` runs the same task in several worktrees and only compares; `/apply-worktree` brings one result into the main checkout. — [Cursor docs, worktrees](https://cursor.com/docs/configuration/worktrees)
- **VM per child, coordinator resolves (Devin).** Each managed Devin has its own VM; the coordinator "resolves any conflicts" and compiles results, with the method unspecified. — [Cognition, "Devin can now manage Devins"](https://old.cognition.ai/blog/devin-can-now-manage-devins)
- **Single-threaded writes (Cognition, 2026-04-22).** The pattern Cognition endorses keeps one writer and uses other agents as reviewers or advisers; the writer filters reviewer findings against the user's instructions. — [Cognition, "Multi-Agents: What's Actually Working"](https://cognition.com/blog/multi-agents-working)
- **Locks on shared coordination state failed (Cursor).** Held too long, never released, lost on crash; throughput of 20 agents fell to that of 1 to 3. Optimistic concurrency removed the lock overhead but not the confusion or the risk aversion. — [Cursor, 2026-01-14](https://cursor.com/blog/scaling-agents); [Cursor, 2026-02-05](https://cursor.com/blog/self-driving-codebases)
- **Single integrator agent failed at scale (Cursor).** The integrator "created more bottlenecks than it solved" and was "an obvious bottleneck" with hundreds of workers; it was removed. — [Cursor, 2026-01-14](https://cursor.com/blog/scaling-agents); [Cursor, 2026-02-05](https://cursor.com/blog/self-driving-codebases)
- **Tolerated error rate instead of a gate (Cursor).** Demanding a fully correct tree before each commit serialized the system; the team accepted a small constant error rate and "moments of turbulence" when agents overlapped, paid for in extra tokens. A "green" snapshot branch with a fixup pass is proposed, not shown. — [Cursor, 2026-02-05](https://cursor.com/blog/self-driving-codebases)
- **Re-verification by hooks and CI.** Claude Code `TaskCompleted` hooks can reject completion; GitHub's guidance is to verify tests and CI on each agent PR and to read session logs before merge. — [Claude Code docs, agent teams](https://code.claude.com/docs/en/agent-teams); [GitHub Blog, 2025-12-01](https://github.blog/ai-and-ml/github-copilot/how-to-orchestrate-agents-using-mission-control/)
- **[MEASURED, synthetic] Isolation does not prevent duplicate work.** A June 2026 arXiv study (Sarkar, arXiv:2606.19616), as summarized by a practitioner blog, ran 32 concurrent synthetic deterministic agents (not LLMs): no coordination gave a 78% duplicate-work rate, 410 conflicting edits and 2.33 tasks/round; advisory locks alone 64%, 138 and 3.84; locks plus shared completion state 0%, 48 and 8.00. Lock starvation occurred in all coordinated arms (12 events). — [Daniel Vaughan, "Before the Pull Request", 2026-06-20](https://codex.danielvaughan.com/2026/06/20/before-the-pull-request-multi-agent-coordination-codex-cli-grite-duplicate-work-prevention/) (secondary summary of the paper; the paper itself was not read)

### Inferences
- The conflict-handling options sort into a rough ladder: (1) separate checkouts so writes cannot collide physically; (2) partition by file or module so merges are trivial; (3) task-level claims with dependencies so two agents do not do the same thing; (4) one integrator, human or agent; (5) optimistic shared-branch pushes with tolerated breakage. Products for individual developers stop at 1 to 4 with the human as integrator. Only Cursor's research harness reports operating at 5.
- Worktrees solve write collisions but not semantic conflicts or duplicated effort; a shared record of what is done is a separate requirement (docs for agent teams, the Sarkar study and Cursor's handoffs all point this way).
- Merge queues as such are not described in any of the vendor sources read. The closest reported analogue, Cursor's integrator, was removed.

### Gaps
- No primary source describes an automated merge-conflict resolution algorithm; Devin's coordinator and Cursor's workers are said to resolve conflicts without detail.
- No source read gives a measured merge-conflict rate for real LLM agents working in parallel worktrees.
- The Sarkar paper was read only through a blog summary and uses synthetic agents; its author plans a real-agent study that had not reported.

## 4. How many parallel agents are useful before coordination and review cost dominate

### Takeaway
Vendor documentation and practitioner reports cluster at 3 to 5 coordinated agents, with hard defaults in the 8 to 30 range and hundreds only in Cursor's fully autonomous research harness with no human review in the loop. The binding constraint reported for human-supervised work is review throughput, not tooling.

### Cited Findings
- **[DOCS] Claude Code agent teams.** "Start with 3-5 teammates for most workflows." "If you have 15 independent tasks, 3 teammates is a good starting point." "Having 5-6 tasks per teammate keeps everyone productive". "Three focused teammates often outperform five scattered ones." Token costs scale linearly with teammates; coordination overhead rises and returns diminish. — [Claude Code docs, agent teams](https://code.claude.com/docs/en/agent-teams)
- **[DOCS] Claude Code ceilings.** 20 concurrent subagents per session by default; `/batch` splits into 5 to 30 worktree subagents. — [subagents](https://code.claude.com/docs/en/sub-agents); [Run agents in parallel](https://code.claude.com/docs/en/agents)
- **[MEASURED/prompted] Anthropic Research.** 3 to 5 subagents in parallel as the typical fan-out; more than 10 only for complex research with clearly divided responsibilities. — [Anthropic, 2025-06-13](https://www.anthropic.com/engineering/multi-agent-research-system)
- **[DOCS] Devin.** Example cap of "no more than 10 running at a time" for a per-service audit. — [Cognition, 2026-03-19](https://old.cognition.ai/blog/devin-can-now-manage-devins)
- **[DOCS] Retention defaults as soft ceilings.** Codex keeps 15 managed worktrees by default; Cursor caps at 25 per machine. — [Codex docs](https://learn.chatgpt.com/docs/environments/git-worktrees); [Cursor docs](https://cursor.com/docs/configuration/worktrees)
- **[MEASURED] Cursor harness.** Several hundred concurrent agents per run, about 1,000 commits/hour at peak, limited by disk I/O on one machine; this is with no human review of individual commits, and the largest human-relevant output (the Solid to React migration) "still needs careful review". — [Cursor, 2026-02-05](https://cursor.com/blog/self-driving-codebases); [Cursor, 2026-01-14](https://cursor.com/blog/scaling-agents)
- **[MEASURED, informal] Collapse case.** With flat lock-based coordination, 20 agents produced the throughput of 1 to 3. — [Cursor, 2026-02-05](https://cursor.com/blog/self-driving-codebases)
- **[ANECDOTE] Four per repository.** "We cap ourselves at four concurrent sessions on one repository"; the cap should be set by review throughput, and the suggested test is to run three agents for a week and measure how long each diff waits for review. — [Michael Kerkhoff, Context Studios, 2026-07-21](https://www.contextstudios.ai/blog/run-10-claude-code-agents-review-is-your-real-bottleneck)
- **[ANECDOTE, second-hand] 5 to 7 on a laptop.** Practitioners are reported to hit a ceiling of 5 to 7 concurrent agents before rate limits, merge conflicts and review consume the gains (attributed to an Augment Code guide I did not read). — [Daniel Vaughan, 2026-06-20](https://codex.danielvaughan.com/2026/06/20/before-the-pull-request-multi-agent-coordination-codex-cli-grite-duplicate-work-prevention/)
- **[CLAIM, second-hand] Token overhead.** Independent multi-agent architectures are said to add 58% token overhead, rising to 263% in decentralized designs (attributed to a Medium article I did not read). — [Daniel Vaughan, 2026-06-20](https://codex.danielvaughan.com/2026/06/20/before-the-pull-request-multi-agent-coordination-codex-cli-grite-duplicate-work-prevention/)
- **Task sizing matters as much as agent count.** Too-small tasks make coordination overhead exceed the benefit; too-large tasks run long without check-ins. — [Claude Code docs, agent teams](https://code.claude.com/docs/en/agent-teams)

### Inferences
- Two regimes exist. With a human reviewing each result, useful concurrency is about 3 to 5 and rarely above 10. With no per-change review and an accepted error rate, hundreds of agents can produce volume, but the reported results there are volume metrics with the quality question deferred.
- The consistent "3 to 5" across Anthropic Research, Claude Code agent teams and practitioner reports is a convergence of rules of thumb, not a measured optimum; none of these sources reports a curve of quality or throughput against agent count.

### Gaps
- No controlled measurement of marginal benefit per added agent for real LLM coding agents was found.
- A widely repeated statistic (Faros AI 2025: about 98% more PRs merged and about 91% longer PR review time on high-AI teams) appeared only in a search summary without a resolvable source page; I could not verify it and it should not be cited without checking Faros directly.
- I found no usable reports from Simon Willison or Steve Yegge on agent counts in the searches run.

## 5. Which tasks parallelize well and which do not

### Takeaway
All sources agree on the axis: read-heavy, breadth-first, independently verifiable work parallelizes; tightly coupled writes do not. Mechanical migrations and per-unit jobs (per file, per page, per service) are the main write-side exception because the units share no decisions.

### Cited Findings
- **Reads vs writes.** Read actions are "inherently more parallelizable than write actions"; parallel writing requires passing context between agents and then merging outputs. — [Harrison Chase, LangChain, 2025-06-16](https://www.langchain.com/blog/how-and-when-to-build-multi-agent-systems)
- **Breadth-first research.** Multi-agent systems "excel especially for breadth-first queries" with independent directions, and are economical only when "the value of the task is high enough". — [Anthropic, 2025-06-13](https://www.anthropic.com/engineering/multi-agent-research-system); quoted in [LangChain](https://www.langchain.com/blog/how-and-when-to-build-multi-agent-systems)
- **Poor fit: shared context and dependencies.** Tasks where all agents need the same context or have many dependencies, including most coding tasks. — [Anthropic, 2025-06-13](https://www.anthropic.com/engineering/multi-agent-research-system)
- **Why coupled writes fail.** "Actions carry implicit decisions, and conflicting decisions carry bad results" (2025-06-12); still held "for parallel-writer swarms" on 2026-04-22. — [Cognition 2025](https://cognition.com/blog/dont-build-multi-agents); [Cognition 2026](https://cognition.com/blog/multi-agents-working)
- **Claude Code agent teams: good.** Research and review; new modules or features where each teammate owns a separate piece; debugging with competing hypotheses; cross-layer work (frontend, backend, tests) with one owner each. **Bad:** "sequential tasks, same-file edits, or work with many dependencies". New users are told to start with tasks that "don't require writing code". — [Claude Code docs, agent teams](https://code.claude.com/docs/en/agent-teams)
- **Why parallel review and debugging help.** A single reviewer "tends to gravitate toward one type of issue at a time"; sequential investigation anchors on the first plausible theory, so independent investigators told to disprove each other do better. **[CLAIM]** — [Claude Code docs, agent teams](https://code.claude.com/docs/en/agent-teams)
- **Independent review benefits from not sharing context.** Devin Review works best with a clean context that sees only the diff. **[MEASURED]** 2 bugs per PR on average, about 58% severe. — [Cognition, 2026-04-22](https://cognition.com/blog/multi-agents-working)
- **Codex.** Parallel subagents for exploration, tests, triage and summarization; caution for write-heavy parallel work. — [Codex docs, subagents](https://learn.chatgpt.com/docs/agent-configuration/subagents)
- **GitHub.** Parallel: research, analysis (logs, profiling), documentation generation, security reviews, work in different modules or components. Sequential: tasks with dependencies, unfamiliar territory, complex problems where assumptions need validating between steps. — [GitHub Blog, 2025-12-01](https://github.blog/ai-and-ml/github-copilot/how-to-orchestrate-agents-using-mission-control/)
- **Migrations and per-unit jobs.** Devin: QA per page, icon-library migration, per-service audits, class-to-hooks refactors, end-to-end tests per feature. Claude Code: `/batch` for one large change split into 5 to 30 units; workflows for "a 500-file migration" or codebase-wide audit. Cursor: Solid to React migration (+266K/-193K over three weeks) passed CI but needed careful review. — [Cognition, 2026-03-19](https://old.cognition.ai/blog/devin-can-now-manage-devins); [Claude Code docs](https://code.claude.com/docs/en/agents); [Cursor, 2026-01-14](https://cursor.com/blog/scaling-agents)
- **Best-of-N as a different use of parallelism.** Running the same task several times (optionally on different models) and choosing one result sidesteps merging entirely. — [Cursor docs, worktrees](https://cursor.com/docs/configuration/worktrees)
- **Greenfield builds with a spec.** Cursor's hundreds-of-agents runs were on from-scratch projects (browser, emulator, spreadsheet, LSP) where planners could carve the scope recursively; vague "spec implementation" instructions sent agents toward obscure features. — [Cursor, 2026-02-05](https://cursor.com/blog/self-driving-codebases)

### Inferences
- A workable test before parallelizing: can each unit be specified in a self-contained brief, verified on its own (tests, a screenshot, a cited source), and merged without another unit's decisions? If yes (research, review, per-file migration, test generation per feature), fan out. If the units must agree on an interface or style that is not yet written down, either fix that decision first in a shared artifact or keep one writer.
- Parallelism has four distinct uses in these systems, with different merge needs: breadth (split the space, concatenate findings), redundancy (best-of-N, pick one), adversarial checking (independent reviewer, writer filters), and throughput on separable writes (migration units, one PR each). Only the last needs conflict handling.

### Gaps
- Test generation is named as a good fit by Codex docs and Devin's examples, but no source read gives a measured result for parallel test generation.
- No source read reports a measured failure rate for parallelizing tightly coupled changes; the case against it rests on Cognition's reasoning and example, Anthropic's statement, and Cursor's qualitative reports.
