## 1. Limits on speedup: Amdahl, Gustafson, USL, Brooks. Has anyone fitted them to multi-agent LLM systems?

### Takeaway
No source found fits Amdahl's law or the Universal Scalability Law (USL) to a multi-agent LLM system; USL appears only as an analogy in practitioner writing. The closest measured results show the same shape those laws predict: a contention plateau (Cursor: 20 lock-coordinated agents ran at the throughput of 1 to 3), super-linear coordination cost (Google/MIT: turns grow as n^1.724), and retrograde scaling on sequential tasks (-39% to -70%).

### Cited Findings

Classic results
- **Amdahl's law.** If a fraction p of the work can be parallelised and (1 - p) is serial, speedup on N workers is S(N) = 1 / ((1 - p) + p/N), with the limit 1/(1 - p) as N grows. Amdahl's 1967 paper makes the argument in words (he estimated the sequential "data management housekeeping" share at about 40% of load); the formula is the later standard formalisation. [canonical, not re-fetched] — [Amdahl 1967, AFIPS](https://doi.org/10.1145/1465482.1465560)
- **Gustafson's law.** Scaled speedup = N + (1 - N)·s, where s is the serial fraction of run time measured on the parallel system. Assumes the problem grows with N (fixed time, not fixed size). Gustafson reported speedups of over 1000 on a 1024-processor hypercube at Sandia. [canonical, not re-fetched] — [Gustafson 1988, CACM 31(5)](https://doi.org/10.1145/42411.42415)
- **Universal Scalability Law.** C(N) = N / (1 + α(N - 1) + βN(N - 1)). α is contention (serialisation, queueing; linear in N), β is coherency (cost of keeping copies consistent; quadratic in N). With β = 0 it reduces to Amdahl's law. With β > 0, throughput peaks and then falls (retrograde scaling); the peak is at N* = sqrt((1 - α)/β) (the peak formula is standard Gunther; the formula and the β = 0 reduction were confirmed in the search result). [snippet for the formula; peak formula canonical, not re-fetched] — [Gunther, "A General Theory of Computational Scalability Based on Rational Functions", arXiv 0808.1431](https://ar5iv.arxiv.org/html/0808.1431)
- A course page prints the coherency term as αβN(N - 1); this disagrees with Gunther's own paper and looks like a typesetting error. Use the arXiv form. [snippet] — [Aalto course page](https://csfoundations.cs.aalto.fi/en/courses/designing-and-building-scalable-web-applications/part-1/3-scalability-laws); contradicted by [Gunther arXiv 0808.1431](https://ar5iv.arxiv.org/html/0808.1431)
- **Brooks's law.** "Adding manpower to a late software project makes it later." Reasons given: ramp-up time, and pairwise communication paths that grow as n(n - 1)/2; only perfectly partitionable tasks with no communication scale with headcount. [canonical, not re-fetched] — [Brooks, The Mythical Man-Month, 1975 (summary)](https://en.wikipedia.org/wiki/Brooks%27s_law)

Evidence from LLM-agent systems (all measured unless marked)
- **No USL fit found.** A search for USL applied to multi-agent LLM systems returned only an informal practitioner analogy (ChatBotKit guide), not a fitted model. [snippet] — [ChatBotKit coordination guide](https://chatbotkit.com/guides/multi-agent-coordination-guide)
- **Kim et al., "Towards a Science of Scaling Agent Systems"** (Google Research, MIT and others; arXiv v1 9 Dec 2025, v3 8 Apr 2026). 260 configurations, six agentic benchmarks, five architectures (single agent, independent, centralized, decentralized, hybrid), three model families. Does not mention Amdahl or USL in the first 100,000 characters read. Measured results: [fetched]
  - Change against the single-agent baseline ranges from +80.8% (Finance Agent, centralized: 0.631 vs 0.349) to -70.0% (PlanCraft, independent). On PlanCraft every multi-agent variant lost: -70.0%, -50.3%, -41.5%, -39.1%.
  - SWE-bench Verified (single agent 0.522): hybrid -2.1%, centralized -3.1%, decentralized -5.4%, independent -14.9%.
  - Error amplification against single agent = 1.0: independent 17.2x, decentralized 7.8x, hybrid 5.1x, centralized 4.4x (credited to "validation bottlenecks that intercept errors before aggregation").
  - Token overhead against single agent: independent 58%, decentralized 263%, centralized 285%, hybrid 515%.
  - Successes per 1,000 tokens: single agent 67.7, independent 42.4, decentralized 23.9, centralized 21.5, hybrid 13.6.
  - Turn count against number of agents: T = 2.72 × (n + 0.5)^1.724, R² = 0.974, exponent 95% CI [1.685, 1.763].
  - Capability ceiling: tasks where the single agent already scores above about 45% see negative returns from more agents.
  - Predictive model: cross-validated R² = 0.373 (0.413 with a task-grounded capability metric); picks the best architecture for 87% of held-out configurations.
  — [arXiv 2512.08296 abstract](https://arxiv.org/abs/2512.08296), [full text v3](https://arxiv.org/html/2512.08296v3)
- A related Nature Machine Intelligence 2026 paper from the same group reports that single-agent baseline performance is the most robust predictor of whether coordination helps, and frames the threshold as a selection rule, not a universal law. [snippet] — [UW Ubicomp Lab publication page](https://ubicomplab.cs.washington.edu/publications/Zhihan_NatureMI2026/)
- **Cursor, "Scaling long-running autonomous coding"** (Wilson Lin, 14 Jan 2026). With a shared coordination file and locks: "Twenty agents would slow down to the effective throughput of two or three, with most time spent waiting." Agents "would hold locks for too long, or forget to release them entirely." [fetched] — [Cursor blog](https://cursor.com/blog/scaling-agents)
- **Cursor, "Towards self-driving codebases"** (Wilson Lin, 5 Feb 2026). A central integrator role "became an obvious bottleneck" with hundreds of workers and was removed. Requiring 100% correctness before each commit caused serialisation and stalls; the team accepted a "small and constant" error rate with a later fix-up pass. A planner/executor/worker/judge cycle was "bottlenecked by the slowest worker". Final design reached about 1,000 commits per hour across 10M tool calls in a week, with "linear scaling of token throughput" claimed (no absolute figures). [fetched] — [Cursor blog](https://cursor.com/blog/self-driving-codebases)
- **Anthropic, "How we built our multi-agent research system"** (13 Jun 2025). Multi-agent (Opus 4 lead, Sonnet 4 subagents) "outperformed single-agent Claude Opus 4 by 90.2% on our internal research eval". Multi-agent systems use about 15x the tokens of chat (single agents about 4x). Token usage alone explains 80% of performance variance on BrowseComp. Parallel tool calling "cut research time by up to 90% for complex queries". The lead agent runs subagents synchronously and waits for each batch, which "creates bottlenecks in the information flow between agents". Stated poor fits: tasks where all agents must share one context, tasks with many inter-agent dependencies, and "most coding tasks involve fewer truly parallelizable tasks than research". [fetched] — [Anthropic engineering blog](https://www.anthropic.com/engineering/multi-agent-research-system)
- **Anthropic, "Building a C compiler with a team of parallel Claudes"** (Nicholas Carlini, 5 Feb 2026). 16 agents, nearly 2,000 sessions, about two weeks, just under $20,000, about 100,000 lines of Rust. Parallelism worked while there were many independent failing tests. On one monolithic task (compiling the Linux kernel): "Every agent would hit the same bug, fix that bug, and then overwrite each other's changes"; "Having 16 agents running didn't help because each was stuck solving the same task." Fix: use GCC as a known-good oracle so that each agent compiles a different subset of files with the new compiler, turning one task into many independent ones. [fetched] — [Anthropic engineering blog](https://www.anthropic.com/engineering/building-c-compiler)
- **Cemri et al., "Why Do Multi-Agent LLM Systems Fail?" (MAST)** (UC Berkeley; arXiv Mar 2025, v3 Oct 2025). 1,642 annotated traces from 7 frameworks, 14 failure modes, annotator κ = 0.88. Largest modes: step repetition 15.7%, reasoning-action mismatch 13.2%, unaware of termination conditions 12.4%, disobey task specification 11.8%, incorrect verification 9.1%, no or incomplete verification 8.2%. Category totals of about 44.2% (system design), 32.4% (inter-agent misalignment), 23.5% (verification) are sums computed from the per-mode figures, not numbers quoted from the paper text. The paper states "MAS failure is not merely a function of challenges in the underlying model". [fetched] — [arXiv 2503.13657v3](https://arxiv.org/html/2503.13657v3)
- **LLMCompiler** (Kim et al., UC Berkeley; arXiv Dec 2023). Planner emits a task DAG; executor runs independent calls in parallel. Reported against sequential ReAct: latency speedup up to 3.7x, cost saving up to 6.7x, accuracy up to about 9% better; 1.8x on HotpotQA; up to 1.35x latency gain over OpenAI parallel function calling. [snippet] — [arXiv 2312.04511](https://arxiv.org/abs/2312.04511)

### Inferences
- Back-of-envelope only: Cursor's "20 agents at the throughput of 2 to 3", read through Amdahl's formula, implies a serial (lock-waiting) fraction of roughly 30% to 47% (solve 1/S = s + (1 - s)/20 for S = 3 and S = 2). Cursor did not publish this figure; it is a derived illustration.
- The fitted turn exponent of 1.724 (between linear and quadratic) is what a USL coherency term looks like in practice: cost per added agent rises with the number of agents already present. Nobody has fitted α and β, but the data needed (throughput against agent count at fixed task) is the same data USL takes, so a designer can fit it on their own system with three or four agent counts.
- The serial fraction in agent systems sits in three places: planning/decomposition before fan-out, the lead agent waiting for the slowest worker (synchronous join), and integration/review after. Cursor's history shows each one in turn being the bottleneck (locks, then integrator, then slowest worker).
- Gustafson's framing fits agents better than Amdahl's when the goal is "cover more ground in the same wall-clock time" (research breadth, many failing tests). Amdahl's framing fits "finish this one fixed task sooner" (one bug, one design), where measured results are flat or negative.
- Brooks's caveat carries over directly: gains appear only when the task is partitionable without communication. The Carlini oracle trick is a method for manufacturing partitionability.
- Accuracy, not only speed, has a "serial" term: independent agents with no verification step amplified errors 17.2x, centralized 4.4x. A verification bottleneck costs throughput and buys correctness, so the designer is choosing a point on that curve, not removing the bottleneck.

### Gaps
- No published fit of Amdahl or USL parameters to any LLM multi-agent system was found. Whether USL's functional form fits agent throughput is untested.
- No source reports a directly measured serial fraction (share of wall-clock in planning, merging, review) for a production agent system.
- The Kim et al. text beyond character 100,000 was not read; Amdahl/USL could be mentioned in the unread appendix.
- Cursor's "linear scaling of token throughput" is a vendor claim with no published curve, and token throughput is not the same as useful work.

## 2. Shared-nothing designs: MapReduce, dataflow DAGs, futures, fork-join and work stealing

### Takeaway
MapReduce's guarantee (re-execute any failed task and get the same answer) depends on deterministic functions and atomic commit of each task's output; LLM workers are not deterministic, so the properties that survive are immutable inputs, isolated per-worker workspaces, one atomic output per task, and idempotent commit, with the recorded output (not re-execution) as the source of truth. The agent systems that scaled furthest (Anthropic research subagents, Cursor's final hierarchy) are shared-nothing fan-out with results passed upward.

### Cited Findings

Classic results
- **MapReduce** (Dean and Ghemawat, OSDI 2004). User supplies map (key/value to intermediate key/value pairs) and reduce (merge values per key). Fault tolerance is by re-execution: a failed worker's tasks are rescheduled. Each task writes to private temporary files and commits by atomic rename, so only one execution's output is visible. With deterministic map and reduce, output equals that of a non-faulting sequential run; with non-deterministic operators the paper gives only weaker semantics (output of a given reduce task corresponds to some sequential execution, and different reduce tasks may correspond to different ones). "Backup tasks" (speculative duplicates of stragglers) cut tail latency. The optional combiner does partial merging on the map side and needs a commutative and associative reduce function. [canonical, not re-fetched] — [Dean and Ghemawat 2004](https://research.google/pubs/mapreduce-simplified-data-processing-on-large-clusters/)
- **Work stealing** (Blumofe and Leiserson, JACM 1999). For fully strict (fork-join) computations, randomised work stealing on P processors runs in expected time T1/P + O(T∞), where T1 is total work and T∞ is the critical-path length. Idle workers steal from others' queues, so there is no central dispatcher. [canonical, not re-fetched] — [Blumofe and Leiserson 1999](https://doi.org/10.1145/324133.324234)
- **Futures/promises.** A future is a placeholder for a result still being computed; the consumer blocks (or chains) only when it needs the value (Baker and Hewitt 1977; Liskov and Shrira 1988 for promises). [canonical, not re-fetched] — [Futures and promises (overview with references)](https://en.wikipedia.org/wiki/Futures_and_promises)

LLM-agent applications
- **Measured, dataflow DAG:** LLMCompiler plans a dependency DAG of tool calls and runs independent ones in parallel; up to 3.7x latency speedup against sequential ReAct (Dec 2023). [snippet] — [arXiv 2312.04511](https://arxiv.org/abs/2312.04511)
- **Measured, fork-join with synchronous join:** Anthropic's research system (Jun 2025) fans out subagents, each with its own context window, and the lead agent waits for the whole batch. Subagents write results to external storage and "pass lightweight references back to the coordinator", which reduces information loss and token overhead. The lead cannot steer running subagents and subagents cannot coordinate with each other. [fetched] — [Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system)
- **Measured, shared-nothing hierarchy:** Cursor's final design (Feb 2026) is a recursive tree of root planners, sub-planners and workers. Workers "operate on their own repo copy", are unaware of the larger system, do not talk to other workers, and return a single handoff to the planner that requested the work. Earlier manual fan-out from a dependency graph raised throughput but agents "couldn't communicate with each other". [fetched] — [Cursor](https://cursor.com/blog/self-driving-codebases)
- **Measured, pull-based claiming (close to work stealing, without the deque):** in the Carlini compiler project (Feb 2026) there was no orchestrator; each of 16 agents picked the "next most obvious" problem and claimed it by writing a file under `current_tasks/`. It worked while the task pool was wide (many failing tests) and failed when the pool collapsed to one task. [fetched] — [Anthropic](https://www.anthropic.com/engineering/building-c-compiler)
- **Measured, deterministic partitioning of a shared test load:** the same project used a `--fast` mode that runs a deterministic per-agent random sample of tests, different on each VM, so the union covers the whole suite while each agent can still detect its own regressions. [fetched] — [Anthropic](https://www.anthropic.com/engineering/building-c-compiler)
- **Measured, the cost of no reduce-side check:** independent agents with outputs simply aggregated amplified errors 17.2x against a single agent; a centralized checker cut this to 4.4x (Kim et al., Dec 2025). [fetched] — [arXiv 2512.08296v3](https://arxiv.org/html/2512.08296v3)

### Inferences
- Ranking of MapReduce properties for LLM workers, from most to least transferable:
  1. Immutable inputs (each worker reads a fixed snapshot: a commit hash, a frozen document). This is what makes a retry or a second opinion comparable at all.
  2. Private workspace plus atomic commit of one output per task (MapReduce's temp file and rename; for agents a worktree/branch and a merge, or a result file and a reference). Partial work is never visible.
  3. Idempotent commit keyed by task ID, so a duplicate or late worker cannot commit twice. Needed because speculative duplicates and crash retries are normal.
  4. Determinism does not transfer. Re-running an LLM task gives a different output, so "re-execute to recover" becomes "re-execute to get a replacement", and anything downstream that consumed the first output is now inconsistent with the second. Hence: record the output once and treat the record as truth (see section 6).
- MapReduce's weaker guarantee for non-deterministic operators is the accurate model for agent fan-out: each task's output is some valid run, but two tasks may have been produced under different, mutually inconsistent assumptions. The reduce step therefore has to check cross-task consistency, which is real work and part of the serial fraction.
- Combiner analogue: partial summaries can be merged safely only if the merge is associative and commutative (set union of findings with sources, counts, max). Free-text summarise-the-summaries is neither, so the order and grouping of merges changes the result.
- Backup tasks transfer well: LLM workers have long-tailed completion times and stall, so launching a duplicate of a straggler and taking the first valid result is cheap relative to waiting, provided commit is idempotent.
- Work stealing's bound T1/P + O(T∞) says the critical path sets the floor. For agents the critical path is the chain of steps that each need the previous step's output, and that is where measured multi-agent results go negative (PlanCraft).
- Futures are the right handle for a subagent result: hand the parent a reference, let it continue with other work, and block only at the point of use. Anthropic's synchronous batch join is the simple version; they name it as a bottleneck.

### Gaps
- No source measured the benefit of speculative duplicate agents (backup tasks) for LLM work.
- No source found reports a true work-stealing scheduler (per-worker deques, stealing) for LLM agents with measurements; the systems found use a shared task pool or a planner that hands out tasks.
- The LLMCompiler figures come from a search summary, not from reading the paper in this session.

## 3. Shared-state designs: blackboard, Linda tuple spaces, actors and supervision, CSP channels

### Takeaway
Blackboards and tuple spaces decouple agents (no one needs to know who else exists) and have measured accuracy gains in 2025 LLM papers, but they move the hard problem into control (who acts next) and into claim discipline, which LLM agents follow unreliably. Actors with supervision fit agents that crash or wander, and are the base of AutoGen v0.4; published measurements of supervision trees for LLM agents were not found.

### Cited Findings

Classic results
- **Blackboard / Hearsay-II** (Erman, Hayes-Roth, Lesser, Reddy, ACM Computing Surveys 1980). Three parts: a shared, structured blackboard of hypotheses at several levels of abstraction; independent knowledge sources that each watch for a condition and contribute a change; a control component (scheduler with an agenda) that chooses which triggered knowledge source runs next. Knowledge sources never call each other. Strengths: opportunistic problem solving, easy to add a knowledge source, tolerates uncertain partial results. Limits: control/scheduling is the hard part and carries overhead; the blackboard is a single shared structure. [canonical, not re-fetched] — [Erman et al. 1980](https://doi.org/10.1145/356810.356816)
- **Linda tuple spaces** (Gelernter, TOPLAS 1985, "Generative communication in Linda"). Operations: `out(t)` adds a tuple; `in(template)` removes a matching tuple atomically and blocks if none exists; `rd(template)` reads a matching tuple without removing it; `eval` creates a live tuple (a process). Tuples exist independently of their creator, so sender and receiver are decoupled in space (no names) and time (need not be alive together). Because `in` is atomic removal, a tuple is both a message and a lock/claim. Limits: associative matching is costly, no ordering or fairness guarantee, a process that dies after `in` loses the tuple unless transactions or leases are added (as JavaSpaces later did). [canonical, not re-fetched] — [Gelernter 1985](https://doi.org/10.1145/2363.2433)
- **Actor model** (Hewitt, Bishop, Steiger 1973; Agha 1986). An actor has private state and a mailbox; on a message it can send messages, create actors, and choose its behaviour for the next message. No shared state; delivery is asynchronous and unordered. [canonical, not re-fetched] — [Agha, Actors, MIT 1985/86](https://dspace.mit.edu/handle/1721.1/6952)
- **Erlang/OTP supervision** (Armstrong, PhD thesis 2003). Processes are isolated and linked; a supervisor restarts failed children according to a strategy (one-for-one, one-for-all, rest-for-one) with a restart-intensity limit, after which the failure escalates upward. "Let it crash": do not repair corrupt state in place; restart from a known-good state. [canonical, not re-fetched] — [Armstrong 2003](https://erlang.org/download/armstrong_thesis_2003.pdf)
- **CSP** (Hoare, CACM 1978). Processes communicate only by synchronous message passing on named channels (rendezvous); a guarded alternative selects among ready communications. Bounded or unbuffered channels give backpressure; the classic failure is deadlock. [canonical, not re-fetched] — [Hoare 1978](https://doi.org/10.1145/359576.359585)

LLM-agent applications
- **Measured, blackboard:** Han and Zhang, "Exploring Advanced LLM Multi-Agent Systems Based on Blackboard Architecture" (arXiv 2507.01701, Jul 2025). System LbMAS: role agents share one blackboard, an LLM control unit picks which agents act each round from the blackboard contents, loop until consensus. Evaluated on commonsense, reasoning and maths datasets. [snippet] — [arXiv 2507.01701](https://arxiv.org/html/2507.01701v1)
- **Measured, blackboard without a controller:** Salemi et al. (Google), "LLM-based Multi-Agent Blackboard System for Information Discovery in Data Science" (arXiv 2510.01285, Sep/Oct 2025). Requests are posted to the blackboard and each agent decides for itself whether to respond, so no coordinator needs to know each agent's expertise. Reported 13% to 57% relative improvement in end-to-end success and up to 9% relative gain in data-discovery F1 over the best baseline on KramaBench and modified DSBench and DA-Code. [snippet] — [arXiv 2510.01285](https://arxiv.org/abs/2510.01285v2)
- **Measured, tuple-space-style observation and claim:** CodeCRDT (Pugachev, arXiv 2510.18893, 18 Oct 2025) has agents coordinate "by monitoring a shared state rather than through explicit message passing". 600 trials (6 tasks, 50 runs per mode): up to 21.1% speedup on some tasks, up to 39.4% slowdown on others, 100% convergence with zero merge failures, 5% to 10% semantic conflicts. [fetched abstract] The search summary adds that it cites Linda and blackboards as its lineage and uses a TODO-claim protocol on a Yjs document; that detail was not confirmed from the abstract. [snippet] — [arXiv 2510.18893](https://arxiv.org/abs/2510.18893)
- **Proposal:** "Coordination as an Architectural Layer for LLM-Based Multi-Agent Systems" (arXiv 2605.03310, May 2026) revisits Linda's generative communication for LLM agents and argues that LLM non-determinism breaks assumptions of older coordination calculi, because meaning drifts across rounds of exchange even when no single step is wrong. [snippet] — [arXiv 2605.03310](https://arxiv.org/pdf/2605.03310)
- **Measured failure of an unsupervised shared claim board:** Cursor (Jan 2026): equal-status agents coordinating through a shared file "would hold locks for too long, or forget to release them entirely", could "fail while holding locks", or would update the file without taking the lock. With optimistic concurrency and no hierarchy, agents became risk-averse: "They avoided difficult tasks and made small, safe changes instead." [fetched] — [Cursor](https://cursor.com/blog/scaling-agents)
- **Measured success of the same pattern at small scale:** 16 agents claiming tasks by writing files under `current_tasks/`, with git push as the arbiter ("git's synchronization forces the second agent to pick a different one"), built a 100,000-line compiler (Feb 2026). [fetched] — [Anthropic](https://www.anthropic.com/engineering/building-c-compiler)
- **Framework adoption, actor model:** AutoGen v0.4 (Microsoft Research, full release Jan 2025) was rebuilt on an actor model: AutoGen Core agents exchange asynchronous typed messages, either direct (RPC-like) or broadcast to topics (pub-sub). Stated motives: observability, control, flexible collaboration patterns, scale. No scaling measurements in the announcement. [snippet] — [Microsoft Research](https://www.microsoft.com/en-us/research/articles/autogen-v0-4-reimagining-the-foundation-of-agentic-ai-for-scale-extensibility-and-robustness/)
- **Measured, coordination primitives matter more than the shared substrate:** AgentRoom (Cho and Lee, arXiv 2608.23740, 24 Aug 2026, v2 12 Nov 2026, NeurIPS 2026) exposes file-level `claim`, `status` and `broadcast` as MCP tools over a shared filesystem and concludes "Coordination, not parallelism or CRDT-merge, is the key design choice." [fetched abstract] — [arXiv 2608.23740](https://arxiv.org/abs/2608.23740)
- **Measured, what goes wrong between agents:** MAST (Mar to Oct 2025) records inter-agent failure modes such as ignored other agent's input 1.9%, information withholding 0.85%, task derailment 7.4%, conversation reset 2.2%, and termination failures (unaware of termination conditions 12.4%, premature termination 6.2%). [fetched] — [arXiv 2503.13657v3](https://arxiv.org/html/2503.13657v3)

### Inferences
- Choosing among the four:
  - Blackboard: use when the problem is ill-structured and no one can plan the decomposition ahead (discovery, diagnosis). Budget for the control component; the two 2025 papers differ exactly there (LLM controller against self-selection). Self-selection removes the controller bottleneck and risks duplicate or no response.
  - Tuple space: use for a task pool with atomic claims. `in` gives exactly-one-taker for free, but only if the store enforces it; an LLM asked to "check the file then write your name" is doing a non-atomic read-then-write, which is the Cursor failure. Enforce claims in a tool (database row, git ref, atomic file create), never in the prompt.
  - Actors with supervision: use when workers are expected to crash, loop or wander. The supervisor is ordinary code holding the restart policy and the retry budget; a wandering agent is treated as a crashed one after a deadline. MAST's termination and repetition failures (step repetition 15.7%, unaware of termination 12.4%) are the cases a supervisor with timeouts and restart limits is built for.
  - CSP channels: use for pipelines where backpressure matters (a reviewer that is slower than producers). Rendezvous blocks producers, which makes the bottleneck visible; LLM agents blocked for minutes are costly idle time, so bounded queues are usually preferable to pure rendezvous.
- A tuple that is removed by `in` and whose taker then dies is lost. For agents that take minutes and crash often, the claim must be a lease with expiry, not a removal (section 4).
- "Let it crash" suits LLM agents particularly well because a long, confused context is corrupt state; restarting with a fresh context from the last recorded handoff is the cheap repair. Cursor's judge-then-fresh-iteration cycle and rewritten (not appended) `scratchpad.md` are instances of this.
- Shared boards tend to produce conservative behaviour when no one owns outcomes (Cursor's risk-averse agents). Ownership (hierarchy, assignment) is a separate design choice from the data structure and has to be supplied as well.

### Gaps
- No dedicated Linda-style tuple-space framework for LLM agents with published measurements was found; CodeCRDT and one 2026 position paper are the nearest.
- No published measurement of Erlang-style supervision trees applied to LLM agents (restart rates, recovery success) was found. AutoGen v0.4's actor redesign is reported without scaling data.
- No CSP-specific LLM-agent paper was found.
- The two blackboard papers were seen as search summaries only; their baselines and task details were not checked.

## 4. Concurrency control for shared artifacts: locks and leases with fencing, optimistic control, MVCC, sagas, merge queues

### Takeaway
For agents that take minutes per step and may crash or wander, long-held locks performed worst in the one detailed field report (Cursor), and the working designs are isolated copies (snapshot per agent) with validation at commit time, plus a lease with expiry and a fencing token wherever exclusive ownership is truly required. Merge queues give correctness at the cost of a serial stage that became a bottleneck at hundreds of agents.

### Cited Findings

Classic results
- **Leases** (Gray and Cheriton, SOSP 1989). A lease is a time-limited grant; if the holder fails, the grant expires on its own. Correctness depends on bounded clock drift and on the holder stopping when the term ends. [canonical, not re-fetched] — [Gray and Cheriton 1989](https://doi.org/10.1145/74851.74870)
- **Fencing tokens** (Kleppmann, 8 Feb 2016). A lease alone is unsafe: a client can pause (for example in garbage collection) past its expiry and then write. "You cannot fix this problem by inserting a check on the lock expiry just before writing back to storage." Fix: the lock service issues a number that increases with every grant; the client sends it with each write; the storage service rejects any write whose token is lower than one it has already seen. Example: client 1 gets token 33 and stalls, client 2 gets 34 and writes, client 1's later write with 33 is rejected. This "requires the storage server to take an active role in checking tokens." Kleppmann also separates locks for efficiency (failure costs duplicated work) from locks for correctness (failure corrupts data). [fetched] — [Kleppmann, "How to do distributed locking"](https://martin.kleppmann.com/2016/02/08/how-to-do-distributed-locking.html)
- **Optimistic concurrency control** (Kung and Robinson, TODS 1981). Three phases: read (work on private copies), validate (check that nothing read has changed), write. No locks are held; a failed validation restarts the transaction. Good when conflicts are rare; under high conflict, work is wasted and long transactions can starve. Compare-and-swap and version-number checks are the single-object form. [canonical, not re-fetched] — [Kung and Robinson 1981](https://doi.org/10.1145/319566.319567)
- **Snapshot isolation / MVCC** (Berenson et al., SIGMOD 1995). Each transaction reads from a consistent snapshot as of its start; on commit, first-committer-wins applies to write-write conflicts. Readers never block writers. Anomaly: write skew, where two transactions read overlapping data, write disjoint items, and together break a constraint neither breaks alone. [canonical, not re-fetched] — [Berenson et al., "A Critique of ANSI SQL Isolation Levels"](https://www.microsoft.com/en-us/research/publication/a-critique-of-ansi-sql-isolation-levels/)
- **Sagas** (Garcia-Molina and Salem, SIGMOD 1987). A long-lived transaction is split into steps T1..Tn, each committing on its own, each with a compensating step Ci. Either all Ti complete, or the completed prefix is undone by running compensations in reverse (T1..Tj, Cj..C1). No isolation: intermediate states are visible to others. Compensation is semantic undo, not rollback, and some actions cannot be compensated. [canonical, not re-fetched] — [Garcia-Molina and Salem 1987](https://doi.org/10.1145/38713.38742)
- **Merge queue ("not rocket science rule")** (Graydon Hoare, 2014; Bors). "Automatically maintain a repository of code that always passes all the tests": changes are tested against the tip they will actually land on, one at a time or in batches that are bisected on failure. Trades landing throughput for a mainline that is always green. [canonical, not re-fetched] — [Graydon Hoare, "technicalities: 'not rocket science'"](https://graydon2.dreamwidth.org/1597.html)

LLM-agent evidence
- **Measured, pessimistic locks failed:** Cursor (Jan and Feb 2026): locks held too long or never released; agents crashed holding locks; agents wrote without acquiring the lock; 20 agents ran at the throughput of 1 to 3. Locking was "easy to get wrong and narrowly correct", and more prompting did not fix it. [fetched] — [Cursor, Jan 2026](https://cursor.com/blog/scaling-agents), [Cursor, Feb 2026](https://cursor.com/blog/self-driving-codebases)
- **Measured, optimistic control was better but not sufficient:** Cursor replaced locks with "agents read state freely, and writes failed if state had changed since the last read"; simpler and more robust, it "reduced overhead but didn't eliminate confusion", and without ownership agents avoided hard tasks. [fetched] — [Cursor, Jan 2026](https://cursor.com/blog/scaling-agents)
- **Measured, snapshot per agent with merge at push:** Cursor's final design gives each worker its own repo copy; hundreds of workers pushed to one branch "with minimal conflicts", and overlapping edits were tolerated as "moments of turbulence" that converge at extra token cost. Carlini's project gives each agent its own container and clone; on finishing, the agent pulls, merges, pushes and removes its claim file: "Merge conflicts are frequent, but Claude is smart enough to figure that out." [fetched] — [Cursor, Feb 2026](https://cursor.com/blog/self-driving-codebases), [Anthropic, Feb 2026](https://www.anthropic.com/engineering/building-c-compiler)
- **Measured, optimistic control without convergence:** on a single shared hard task, 16 agents each fixed the same bug and "overwrite each other's changes". [fetched] — [Anthropic, Feb 2026](https://www.anthropic.com/engineering/building-c-compiler)
- **Measured, serial integration stage:** Cursor's integrator role "created more bottlenecks than it solved" and was removed; strict green-before-commit caused stalls, replaced by a tolerated small error rate plus a final green snapshot and fix-up pass. In Carlini's project, late-stage regressions were handled the other way, by adding CI with stricter enforcement so new commits could not break existing code. [fetched] — [Cursor, Feb 2026](https://cursor.com/blog/self-driving-codebases), [Anthropic, Feb 2026](https://www.anthropic.com/engineering/building-c-compiler)
- **Tooling, merge queue for agents:** Gas Town (Steve Yegge, released Jan 2026) runs ephemeral workers in isolated git worktrees that produce merge requests; a per-project "Refinery" lands them through a Bors-style batching and bisecting queue with verification gates. Sources disagree on whether the Refinery resolves conflicts itself or escalates. No throughput measurements found. [snippet] — [Gas Town repository](https://github.com/gastownhall/gastown), [Gas Town architecture doc](https://gastown.dev/docs/design/architecture)
- **Shared build tools as hidden locks:** Cursor names Git and Cargo as contention points (many agents running `git restore`; hundreds of concurrent compiles producing "many GB/s" of disk I/O) and suggests copy-on-write and deduplication as an untested direction. [fetched; the remedy is a proposal] — [Cursor, Feb 2026](https://cursor.com/blog/self-driving-codebases)
- **Published design, sagas:** SagaLLM (Chang and Geng, Stanford; arXiv 2503.11951, Mar 2025; PVLDB vol. 18) applies the saga pattern to multi-agent LLM planning with persistent memory, automated compensation and independent validation agents; it relaxes ACID and claims workflow-wide consistency and recovery. Evaluation is mainly travel-style planning; numbers were not read. [snippet] — [arXiv 2503.11951](https://arxiv.org/abs/2503.11951v3)
- **Measured, file-level claims as advisory locks:** AgentRoom's `claim`/`status`/`broadcast` tools account for most of its gain over an unco-ordinated parallel-merge baseline (authors' ordering claim, Aug to Nov 2026). [fetched abstract] — [arXiv 2608.23740](https://arxiv.org/abs/2608.23740)

### Inferences
- Fit for minute-long, crash-prone, wandering agents:

| Mechanism | Fit | Why |
| --- | --- | --- |
| Lock with no expiry | Poor | Holder crashes or forgets; measured collapse at Cursor. |
| Lease with expiry, no fencing | Unsafe for correctness | An agent that stalls or wanders past expiry still writes. An LLM agent mid-step is Kleppmann's GC pause, lasting minutes. |
| Lease plus fencing token checked by the store | Good where exclusivity is needed | Stale writers are rejected mechanically. The check must sit in the tool or store, since the agent cannot be trusted to self-check. |
| Version check / compare-and-swap at commit | Good default | No waiting; a crash costs nothing to others. Cost is wasted work on conflict, which is expensive when a step costs minutes and dollars, so keep conflict probability low by partitioning. |
| Snapshot per agent (worktree, clone), merge at end | Best measured | Readers and writers never block. Watch for write skew: two agents make individually valid changes that jointly break an invariant. Text merge will not see it; tests or a reviewer must. |
| Saga with compensation | Needed for external side effects | Agent steps commit independently and cannot be rolled back; define a compensation for each, and place non-compensable steps (emails, payments) last or behind approval. |
| Merge queue | Good for a must-stay-green mainline | It is a deliberate serial stage; throughput is bounded by test time per batch. Batching and bisection raise the bound. Cursor dropped strictness to keep throughput; Carlini added it to stop regressions. |

- Kleppmann's efficiency/correctness split is the first question to ask of any agent claim. A task claim that only prevents duplicated work can be a cheap advisory lease (Carlini's `current_tasks/` files, AgentRoom's `claim`). A claim that guards an artifact against corruption needs fencing or commit-time validation.
- Git already gives snapshot isolation (each clone is a snapshot) and first-committer-wins on a ref (a non-fast-forward push is rejected, which is a compare-and-swap on the branch head). That explains why both large field reports settled on plain git push as the arbiter.
- Optimistic control wastes the loser's work. With LLM steps that waste is large per conflict, so the conflict rate has to be driven down by decomposition (disjoint files or modules, ownership), which is what Cursor's hierarchy and Carlini's oracle trick both do.
- Starvation under optimistic control (a long task that keeps losing validation to short ones) is a classic result and matches Cursor's observation that agents drift toward small safe changes.

### Gaps
- No published measurement of lease-plus-fencing for LLM agents was found; the recommendation is carried over from distributed-systems practice.
- No measured conflict rates (share of agent commits needing a merge or retry) were published by Cursor or Anthropic beyond "minimal" and "frequent".
- No throughput data for agent merge queues (Gas Town Refinery or others) was found, and sources disagree on its conflict handling.
- SagaLLM's evaluation numbers were not verified.
- No source addressed write skew between agents by that name; the semantic-conflict figures in section 5 are the nearest evidence.

## 5. Convergent structures: CRDTs, operational transformation, append-only logs and event sourcing, Merkle DAGs and three-way merge

### Takeaway
CRDTs for LLM agents have been published and measured (CodeCRDT 2025, AgentRoom 2026, a multi-user writing tool 2025): they deliver convergence with zero merge failures, but 5% to 10% of merged results were semantically wrong, and AgentRoom attributes its gains to claim/status/broadcast coordination, not to the CRDT merge. Convergence of bytes is solved; agreement of meaning is not, so a CRDT or git merge needs a validation step after it.

### Cited Findings

Classic results
- **CRDTs** (Shapiro, Preguiça, Baquero, Zawirski, 2011). Strong eventual consistency: replicas that have received the same set of updates are in the same state, with no coordination or rollback. State-based CRDTs need states forming a join-semilattice with a merge that is commutative, associative and idempotent, and updates that only move up the lattice; operation-based CRDTs need concurrent operations to commute and reliable causal delivery. Catalogue includes: G-Set (add only; merge is union), 2P-Set (add and remove once), OR-Set (each add carries a unique tag; a remove deletes only the tags it has observed, so a concurrent add wins), LWW-Register (highest timestamp wins; the concurrent loser is silently dropped), counters, and sequence CRDTs for text (RGA, Logoot, Treedoc). [canonical, not re-fetched] — [Shapiro et al., INRIA RR-7506, "A comprehensive study of Convergent and Commutative Replicated Data Types"](https://inria.hal.science/inria-00555588)
- **Operational transformation** (Ellis and Gibbs, SIGMOD 1989). Concurrent operations are transformed against each other so that all sites converge; in practice needs a central server to order operations, and the transformation functions are hard to prove correct. [canonical, not re-fetched] — [Ellis and Gibbs 1989](https://doi.org/10.1145/67544.66963)
- **Local-first software** (Kleppmann, Wiggins, van Hardenberg, McGranaghan, 2019). Argues for CRDTs as the basis for collaboration where each participant holds a full copy and works offline; notes that automatic merge resolves conflicts at the data level and that conflicts of intent still need people. [canonical, not re-fetched] — [Ink and Switch, "Local-first software"](https://www.inkandswitch.com/essay/local-first/)
- **Append-only log / event sourcing.** State is derived by folding over an ordered, immutable sequence of events; the log is the source of truth, current state is a cache that can be rebuilt, and any past state can be reconstructed. Costs: schema evolution of old events, replay time (mitigated by snapshots), and a total order needs a single sequencer or consensus. [canonical, not re-fetched] — [Fowler, "Event Sourcing"](https://martinfowler.com/eaaDev/EventSourcing.html), [Kreps, "The Log"](https://engineering.linkedin.com/distributed-systems/log-what-every-software-engineer-should-know-about-real-time-datas-unifying)
- **Content-addressed store / Merkle DAG (git).** Every blob, tree and commit is named by the hash of its content; a commit names its tree and parents, so a commit ID fixes the whole history and content beneath it. Objects are immutable; only refs move. Three-way merge compares two tips against their common ancestor and merges non-overlapping changes textually; it detects overlapping text edits, not semantic conflicts. [canonical, not re-fetched] — [Pro Git, "Git Internals - Git Objects"](https://git-scm.com/book/en/v2/Git-Internals-Git-Objects)

LLM-agent applications
- **Measured: CodeCRDT** (Pugachev, arXiv 2510.18893, 18 Oct 2025; single author, preprint, one version). Lock-free concurrent code generation on CRDTs with strong eventual consistency. 600 trials (6 tasks, 50 runs per mode). Up to 21.1% speedup on some tasks; up to 39.4% slowdown on others. 100% convergence, zero merge failures. Semantic conflict rate 5% to 10%. Outcome depends on task structure. [fetched abstract] — [arXiv 2510.18893](https://arxiv.org/abs/2510.18893)
- **Measured: AgentRoom** (Cho and Lee, arXiv 2608.23740; 24 Aug 2026, v2 12 Nov 2026; NeurIPS 2026). "Realtime collaborative editing protocol for concurrent coding agents" on a CRDT-merged shared filesystem. Five frontier coding-CLI models, four backend coding tasks, cross-language checks (Python DevBench, Rust with axum). Motivation: a single agent "abandons up to half of hard tasks with a one-file stub-and-exit". With two agents, AgentRoom abandons fewer tasks than solo and varies less across runs (for "CLI-stable" models). At matched compute one LLM-judge contrast against parallel-merge is positive on average; a "bundle probe" ranks full AgentRoom above each partial configuration (an ordering, not a percentage). Conclusion: "Coordination, not parallelism or CRDT-merge, is the key design choice." [fetched abstract] — [arXiv 2608.23740](https://arxiv.org/abs/2608.23740)
- Caution on AgentRoom: a search summary of the project page says that validity audits found an earlier headline figure was an artefact of a scorer problem and a CRDT bridge bug. Not verified by opening the page. [snippet] — [AgentRoom project page](https://seonglae-agentroom.hf.space/)
- **Measured (user study style): mixed human and agent editing.** "Collaborative Document Editing with Multiple Users and AI Agents" (arXiv 2509.11826, Sep 2025) uses Yjs CRDTs for real-time sync with GPT-4o-mini agents in a writing tool. Findings not read. [snippet] — [arXiv 2509.11826 (summary page)](https://api.emergentmind.com/papers/2509.11826)
- **Practitioner pattern:** ElectricSQL blog, "AI agents as CRDT peers with Yjs" (8 Apr 2026): give the agent its own replica of the document as a peer, and anchor its edits with Yjs relative positions so they stay valid under concurrent edits. Design guidance, no measurements seen. [snippet] — [Electric blog](https://electric.ax/blog/2026/04/08/ai-agents-as-crdt-peers-with-yjs)
- **Measured: git as the convergent store.** Carlini (Feb 2026): shared bare repo, per-agent clones, frequent merge conflicts resolved by the agents, 100,000 lines over about 2,000 sessions. Cursor (Jan and Feb 2026): hundreds of workers pushing to one branch, about 1,000 commits per hour at peak, overlapping edits left to converge. [fetched] — [Anthropic](https://www.anthropic.com/engineering/building-c-compiler), [Cursor](https://cursor.com/blog/self-driving-codebases)
- **Measured: rewrite beats append for an agent's own notes.** Cursor moved to a `scratchpad.md` that is rewritten, not appended to, and to single handoffs sent upward. [fetched] — [Cursor, Feb 2026](https://cursor.com/blog/self-driving-codebases)
- **Event-sourced task ledger in tooling:** Gas Town's Beads is a shared work ledger (tasks, fixes, merge requests, agent notes as queryable records) backed by one Dolt database shared across worktrees. No measurements found. [snippet] — [Gas Town architecture doc](https://gastown.dev/docs/design/architecture)
- **Event-sourced execution history:** durable execution engines keep an append-only event history or journal per workflow and rebuild state by replay (Temporal: the Event History is "the source of truth for everything that happens in the Workflow"; Restate: "every step is recorded in a journal"). Detail in section 6. [fetched] — [Temporal docs](https://docs.temporal.io/workflows), [Restate docs](https://docs.restate.dev/ai/patterns/durable-agents)

### Inferences
- What each structure is good for with agents:
  - G-Set / append-only log: findings, observations, events, claims-made. Merge is union, always safe, never loses anything; the cost is that nothing is ever retracted, so supersession needs explicit "supersedes X" entries. Best first choice for shared agent memory.
  - OR-Set: a task set or to-do list where agents add and remove concurrently. Add-wins means a task re-added while another agent removes it survives, which is the safe direction.
  - LWW-Register: status fields only. It discards the concurrent loser silently, so it must not hold anything an agent worked minutes to produce.
  - Sequence CRDT (Yjs and similar): real-time co-editing of one text by agents and people. Guarantees every edit lands and replicas agree; does not guarantee the result compiles or makes sense. CodeCRDT's 5% to 10% semantic conflict rate with 0% merge failures is the measurement of that gap.
  - Git (Merkle DAG plus three-way merge): coarse-grained, branch-per-agent work with explicit conflict surfacing. A conflict is reported and stops the merge, which for code is a feature: the agent has to look. A CRDT never stops.
- CRDT merge answers "can concurrent edits be combined without coordination"; it does not answer "should these two agents have been editing the same thing". AgentRoom's own conclusion is that advisory claims and status broadcast did the work. A designer can get most of the benefit from claims plus git and add a CRDT only when sub-file, real-time interleaving with humans is required.
- Content addressing gives the immutable inputs that section 2 asks for: handing a worker a commit hash or blob hash fixes exactly what it read, makes results cacheable by input hash, and lets a reviewer verify what a result was based on.
- An event log is the natural shape for an agent team's shared record because agents' steps are already discrete, ordered and worth auditing; the same log serves crash recovery (section 6), replay for debugging, and provenance.
- Operational transformation offers nothing over CRDTs for agents unless a central server already exists; no agent work using it was found.

### Gaps
- CodeCRDT's mechanism details (TODO claim protocol, Yjs, write-verify) come from a search summary and were not confirmed in the abstract. It is a single-author preprint with six tasks.
- AgentRoom's absolute numbers, CRDT library and ablation sizes were not on the abstract page; the reported audit caveat is from a search summary only.
- No published use of OR-Sets, LWW registers or other non-sequence CRDTs specifically for agent task boards or shared memory, with measurements, was found.
- No paper was found that evaluates an event-sourced shared log as the coordination medium between LLM agents (as distinct from per-workflow durable-execution journals).
- No measured comparison of CRDT shared workspace against git worktrees plus merge for the same agent tasks was found beyond AgentRoom's single "parallel-merge" contrast.

## 6. Durable execution and exactly-once effects: journaling, replay, idempotency keys, recording non-deterministic LLM steps

### Takeaway
Durable execution engines handle LLM non-determinism the same way they handle any external call: the orchestration code must be deterministic, each LLM or tool call runs as a recorded step, and on recovery the recorded result is returned instead of calling the model again. This gives effectively-once orchestration; exactly-once external side effects still depend on idempotency keys at the receiving service, and a step that crashes after acting but before its result is recorded will run again.

### Cited Findings

Mechanism (vendor documentation, fetched)
- **Temporal.** Workflow code must be deterministic: it "has to make the same decisions when given the same history" and "shouldn't depend on any values not recorded in the history which would be different between runs" (wall-clock time, random numbers, direct network calls). Recovery does not restore memory: "It starts the Workflow code from the beginning, replays the Event History step by step." Activities hold the non-deterministic work: "the Activity runs once, its result is recorded in the Event History", and on replay "that result is reused, not recomputed". If replayed values differ, "the Workflow could take a different path and fail to match the recorded history." [fetched] — [Temporal docs, Workflows](https://docs.temporal.io/workflows)
- **Restate.** "every step is recorded in a journal"; LLM responses are "persisted so responses are not re-fetched on recovery"; tool executions are "wrapped in durable steps so side effects are not duplicated"; on restart completed steps are "replayed from the journal (no re-execution)" and execution "resumes from the first incomplete step". The page claims "Side effects are executed exactly once. On recovery, the result is replayed." without explaining the mechanism beyond the journal and `ctx.run()`. [fetched] — [Restate docs, durable agents](https://docs.restate.dev/ai/patterns/durable-agents)
- **LangGraph.** Checkpointers "persist a thread's graph state as checkpoints", scoped by `thread_id`, supporting resume after interruption, time travel and fault tolerance; each subgraph has its own checkpoint namespace. The page fetched did not cover determinism or idempotency requirements. [fetched] — [LangChain docs](https://docs.langchain.com/oss/python/langgraph/durable-execution)

Mechanism (search summaries only)
- **DBOS.** Its Vercel AI SDK integration checkpoints every agent action in Postgres and replays from checkpoints after interruption; Pydantic AI's DBOS integration checkpoints ordinary Python functions into Postgres or SQLite. One commentary says a step's output commits in the same Postgres transaction as rows the step wrote. [snippet] — [DBOS docs](https://docs.dbos.dev/integrations/vercel-ai), [Pydantic AI docs](https://ai.pydantic.dev/durable_execution/dbos)
- **Pydantic AI with Temporal.** A `TemporalAgent` wrapper moves model calls, tool executions and external API calls into Temporal Activities with retry policies; durable execution support was described as beta. [snippet] — [Pydantic AI docs](https://ai.pydantic.dev/temporal), [Temporal blog](https://temporal.io/blog/build-durable-ai-agents-pydantic-ai-and-temporal)
- **Limits noted by practitioners.** (a) A checkpointer alone does not know that a step called a payment API, so it cannot stop a replay from calling it again. (b) A database transaction cannot be held open across an LLM call lasting minutes. (c) If the prompt template changes between the original run and the replay, a journalled LLM response may no longer match the current code; treat as a versioning problem. [snippet] — [Tian Pan, "Durable Agents", 23 Apr 2026](https://tianpan.co/blog/2026-04-23-durable-agents-async-queue-workflow-checkpoint)
- **Measured (one informal test), Oct 2026.** A four-framework comparison reports that LangGraph and Mastra checkpoint into the user's database and re-execute the interrupted step, while Pydantic AI and the OpenAI Agents SDK delegate to Temporal or DBOS. In its test a completed plan node ran once and a charge node that crashed mid-step ran twice. [snippet] — [Developers Digest, "Durable AI Agent Frameworks Compared"](https://www.developersdigest.tech/blog/durable-ai-agent-frameworks-compared-2026)
- A developer write-up claims Temporal fails a run if a replayed model call returns different text. This conflicts with the documented behaviour that Activity results are reused from history and not recomputed on replay; the documented behaviour is the one to rely on. [snippet] — [dev.to post](https://dev.to/pickuma/temporal-hits-3000-customers-durable-execution-for-ai-agent-workflows-1p1f); contradicted by [Temporal docs](https://docs.temporal.io/workflows)

Field evidence from agent builders
- **Anthropic (Jun 2025)**, proposal-level description of their production system: long-running agents need to "durably execute code and handle errors along the way"; "we built systems that can resume from where the agent was" instead of restarting; they combine model adaptability with deterministic safeguards such as retry logic and regular checkpoints. No recovery-rate numbers given. [fetched] — [Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system)
- **SagaLLM (Mar 2025, PVLDB 18)** pairs persistent logged state with compensation for multi-agent plans; see section 4. [snippet] — [arXiv 2503.11951](https://arxiv.org/abs/2503.11951v3)

### Inferences
- The rule that makes LLM steps safe under replay: the LLM call is an effect, never part of the deterministic orchestration. Call once, write the output to the journal, and from then on every consumer (the orchestrator on replay, downstream agents, reviewers) reads the recorded output. This is the same answer section 2 reaches for MapReduce with non-deterministic workers.
- The granularity of recorded steps sets the cost of a crash. If a whole multi-minute agent run is one step, a crash repeats all of it; if each model call and each tool call is a step, a crash repeats at most one call. Finer steps cost journal volume and replay time.
- "Exactly once" in vendor text means the orchestrator observes each step's result once. The step itself runs at least once: a crash after the external action and before the journal write causes a re-run (the charge node that ran twice). To close that window each side-effecting tool call needs an idempotency key derived from stable identifiers (workflow ID plus step number), honoured by the receiving service, or a compensation (saga).
- An LLM agent retrying a tool call on its own initiative (same intent, new call) defeats engine-level deduplication because the engine sees a new step. Idempotency keys should therefore be derived from the intent (task ID plus action plus target), not generated per call by the model.
- Replay requires the orchestration code to be deterministic given the journal. An agent loop where the model picks the next step is still deterministic in this sense, because the model's choice is a recorded result; what breaks replay is changing code, prompts or tool schemas mid-run, so long-lived agent workflows need versioning.
- Durable execution covers one workflow's crash recovery. It does not by itself coordinate several agents writing to a shared artifact; that still needs the concurrency control of section 4. The two combine naturally: the journal gives a stable step identity that can serve as both idempotency key and fencing token source.
- Checkpoint-only frameworks (state snapshot at node boundaries) and journal-replay engines differ in what they promise on an interrupted step; the designer should ask of any framework: "after a crash in the middle of a tool call, is the call repeated, and what stops the second call from acting twice?"

### Gaps
- No vendor or paper was found reporting measured recovery rates, duplicate-effect rates or overhead for durable-execution-backed LLM agents; the evidence is documentation, design posts and one informal four-framework test seen only as a summary.
- Temporal's Activity idempotency guidance (at-least-once execution) was not on the page fetched; the statement that activities should be idempotent is standard guidance but is not cited here from a fetched page.
- Restate features relevant to multi-agent work (virtual objects as single-writer state, awakeables for human approval, saga support) were not on the page fetched and are not confirmed here.
- DBOS claims are from search summaries, not from DBOS documentation read in this session.
- No source was found on journalling when an LLM provider streams partial output and the process dies mid-stream, or on reconciling a re-generated (different) LLM output with downstream work that consumed the first one.
