# Parallel agents win when writes stay single

Parallel LLM agents work when one coordinator hands self-contained briefs to a few isolated workers, each worker returns one typed record with its evidence, and plain code (not a model, and not the workers themselves) schedules, combines and checks the results. That shape is where the measured gains sit: up to +80.8% on decomposable analysis, 1.4x to 3.7x wall-clock speedup on independent tool calls, and large gains on inputs longer than the model's usable window. Outside it the measured picture is poor: the mean effect of multi-agent coordination across 260 controlled configurations was -3.5%, every topology lost 39% to 70% on sequential planning, token cost ran 1.6x to 6.2x a single agent (about 15x a chat in one production system), and when budgets are matched a single agent usually ties or wins. The data structures with evidence behind them are a task list with ids and dependency placeholders resolved by code, a fixed-shape result record per unit, an immutable store addressed by reference, an append-only run log, and one isolated workspace per writer with validation at commit. The structures that failed or showed no benefit in the field are shared mutable boards, locks held by agents, peer chat, debate rounds, a single LLM integrator at scale, and CRDT merges, which converge bytes and still produce 5% to 10% semantically wrong results. ContextlessAI already has the hard parts (immutable vault, deterministic packets, engine-owned commits, a cross-provider reviewer, stable atom ids). What it lacks is a typed unit result record with atom-level evidence, a dependency-aware plan that code validates, a reduce step done mostly in code before the assembler writes, and measurements that show whether a plan beat a single call. Evidence strength varies sharply across these claims and is marked throughout; almost nothing has been replicated on 2026 frontier models.

## Production systems converged on hub, spokes and one writer

Three coordination shapes exist in published frameworks, and only one of them dominates production. The first is turn-taking over a shared transcript (ChatDev, AutoGen 0.2 group chat, Magentic-One, Swarm, the OpenAI Agents SDK), where one agent acts at a time and "parallel" is a misnomer. The second is the superstep graph: LangGraph and Microsoft Agent Framework both run every node triggered in a step concurrently, then wait at a synchronization barrier before committing state ([LangGraph Graph API](https://docs.langchain.com/oss/python/langgraph/graph-api); [MAF Workflow Builder and Execution](https://learn.microsoft.com/en-us/agent-framework/concepts/workflows/builder-and-execution)). The third is a free-running event or actor runtime (AutoGen Core, LlamaIndex Workflows, Google ADK ParallelAgent), which gives concurrency with weaker ordering guarantees; ADK's own docs say "the event order is not deterministic" ([ADK Parallel agents](https://adk.dev/agents/workflow-agents/parallel-agents/)). In every case "concurrent" means concurrent model and tool calls, not shared-memory parallelism.

The direction of travel from 2023 to 2026 is away from control flow hidden in a conversation and toward explicit graphs with typed state and checkpoints. AutoGen went from synchronous chat to an actor runtime in January 2025, and its successor adopted Pregel supersteps at general availability in April 2026; Swarm was replaced by the Agents SDK; ADK 2.0 moved to a graph engine ([AutoGen 0.4 launch post](https://devblogs.microsoft.com/autogen/autogen-reimagined-launching-autogen-0-4/); [Visual Studio Magazine](https://visualstudiomagazine.com/articles/2026/04/06/microsoft-ships-production-ready-agent-framework-1-0-for-net-and-python.aspx); [Swarm README](https://github.com/openai/swarm)). This is convergence of design, not measured superiority: **no framework has published a measurement of its concurrency model**, whether speedup, conflict rate or correctness under concurrent writes.

Production coding and research products settled on a narrower shape still. A coordinator composes a brief; workers run in separate context windows and separate checkouts; each returns a summary, a branch or a pull request. Anthropic's research system fans out 3 to 5 subagents with a brief that states objective, output format, tool guidance and task boundaries, and found that short briefs produced duplicated work ([Anthropic engineering](https://www.anthropic.com/engineering/multi-agent-research-system)). Only the reading is parallel there; a single agent writes the final report ([LangChain](https://www.langchain.com/blog/how-and-when-to-build-multi-agent-systems)). Claude Code subagents, Codex subagents and Devin's manager pattern are the same hub and spoke. Cursor's research harness, the largest reported run (several hundred concurrent agents, about 1,000 commits per hour), ended as a tree of planners over workers that are "unaware of the larger system", work on their own repo copy, and return one handoff document upward ([Cursor, Feb 2026](https://cursor.com/blog/self-driving-codebases)).

The two loudest opposing voices now agree. Cognition's 2025 essay argued against multi-agent systems because "actions carry implicit decisions, and conflicting decisions carry bad results"; its April 2026 revision keeps that objection for parallel-writer swarms and endorses "setups where multiple agents contribute intelligence to a task while writes stay single-threaded" ([Cognition 2025](https://cognition.com/blog/dont-build-multi-agents); [Cognition 2026](https://cognition.com/blog/multi-agents-working)). Cursor tried flat peers with a shared lock file, then optimistic concurrency, then a standalone integrator, and removed each ([Cursor, Jan 2026](https://cursor.com/blog/scaling-agents)). Parallelism in these systems serves four different purposes with different merge needs: breadth (split the space and concatenate findings), redundancy (run the same task N times and pick one), adversarial checking (an independent reviewer whose findings the writer filters), and throughput on separable writes (one unit per file, page or service). Only the last needs conflict handling at all.

## Measured gains are narrow, and budget-matched tests mostly erase them

Three readings follow from this table. First, **much of the multi-agent "gain" is extra tokens spread across separate context windows.** Anthropic's own data says token usage alone explained 80% of performance variance on BrowseComp ([Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system)), and a single model executing the same workflow in one conversation matched homogeneous multi-agent versions at lower cost ([Xu et al.](https://arxiv.org/abs/2601.12307)). The benefit is the workflow and the budget, less the separation into agents. Second, the advantage shrinks as base models improve: MetaGPT's HumanEval margin over a single agent fell from 67.0 against 87.7 with ChatGPT to 90.2 against 93.2 with Gemini-2.0-Flash, and coordination gave diminishing or negative returns once the single-agent baseline exceeded about 45% ([Gao et al.](https://arxiv.org/html/2505.18286v1); [Kim et al.](https://arxiv.org/html/2512.08296v2)). Third, the residual wins are specific: inputs past the window's usable length, breadth-first independent lookups, wall-clock latency (Anthropic reports up to 90% less research time, a vendor figure with no controlled counterpart), and hard tasks where the single agent is far from saturation.

The best-supported practical policy is a cascade. Trying the single agent first and escalating to multi-agent only on hard or failed cases beat both pure strategies on most tasks (for example 71.2 against 62.9 and 62.3 on DS1000) while cutting tokens against always-multi-agent ([Gao et al.](https://arxiv.org/html/2505.18286v1)). That paper has internal inconsistencies in its summary figures, so treat the direction as supported and the exact numbers as soft.

## Coordination costs grow faster than the team, and the join fails more than the plan

The costs are measured better than the benefits. Turn count grows as T = 2.72 × (n + 0.5)^1.724 in the number of agents, close to quadratic, and successes per 1,000 tokens fall from 67.7 for a single agent to 13.6 for a hybrid topology ([Kim et al.](https://arxiv.org/html/2512.08296v2)). Nobody has fitted Amdahl's law or the Universal Scalability Law to an agent system, but the shapes those laws predict all appear in field reports: a contention plateau (Cursor's 20 lock-coordinated agents ran at the throughput of 1 to 3), a serial integration stage that became "an obvious bottleneck", and a fan-out "bottlenecked by the slowest worker" ([Cursor, Feb 2026](https://cursor.com/blog/self-driving-codebases)). The serial fraction lives in three places: planning before fan-out, the join waiting for the slowest unit, and integration and review afterward.

Errors compound when nothing checks the join. Independent agents whose outputs were simply aggregated amplified errors 17.2x against a single agent; a central orchestrator cut that to 4.4x, at +285% tokens ([Kim et al.](https://arxiv.org/html/2512.08296v2)). The MAST census of 1,642 failed traces across seven frameworks puts about 44% of failures in system design (step repetition 15.7%, not knowing when to stop 12.4%, disobeying the task specification 11.8%), about 32% in inter-agent misalignment, and about 24% in verification, with "incorrect verification" at 9.1%; the category sums are computed from per-mode figures, and the newest model in the dataset is Claude 3.7 Sonnet ([MAST v3](https://arxiv.org/html/2503.13657v3)). Outright refusal to share is rare (information withholding 0.85%); the common failures are unclear unit contracts and missing stop conditions. Prompt and topology fixes recovered only 9 to 16 points.

The combine step is a larger error source than the decomposition. In LLMCompiler's failure breakdown the planner caused 8% of failures and the final answer step 28% ([LLMCompiler](https://arxiv.org/html/2312.04511v3)). Recursive Language Models report a run that built the correct answer in code and then returned a different one from the root model ([RLM](https://arxiv.org/html/2512.24601v1)). On an open blackboard, full consensus was reached on 89.8% of MMLU problems but only 29.4% of MATH problems, so a merge rule that assumes agreement fails exactly on hard inputs ([LbMAS](https://arxiv.org/html/2507.01701v1)). No source measures the rate at which a merger papers over a real conflict; that gap matters and is worth measuring locally.

Units fail in characteristic ways that data structures can address. A unit whose input lacks the answer tends to invent one; training members to refuse raised correct refusals from 51.0% to 78.6%, and LLM×MapReduce handles the same problem with a literal "NO INFORMATION" return that later stages drop ([LongAgent](https://arxiv.org/html/2402.11550v2); [LLM×MapReduce](https://arxiv.org/html/2410.09342v1)). Units assumed independent when they are not lose quality: Skeleton-of-Thought gained about 2x speed and got worse on math, coding and writing, and its authors added a router that declines to decompose ([Skeleton-of-Thought](https://arxiv.org/html/2307.15337v3)). Units name the same entity differently, which is why DocETL has a Resolve operator before reduce ([DocETL](https://arxiv.org/html/2410.12189v3)). Passing results through a coordinator's context is "a game of telephone"; Anthropic's fix is for subagents to write to external storage and return lightweight references ([Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system)).

Review is weaker than its reputation. GPT-4 as a judge accepted correct GSM8K answers 99.2% of the time and identified incorrect ones only 15.6% ([Wang et al.](https://arxiv.org/html/2406.06461v3)). Prompted to hunt for violations, LLM verifiers swing the other way: 22.5% to 70.4% false positives on matched benign traces, while deterministic rules reached AUROC 0.95 to 0.98 on local violations ([Watching the Watchers](https://neurips.cc/virtual/2026/172886)). Aggressive judge frameworks flip many correct answers to wrong ([Zhang et al.](https://arxiv.org/pdf/2502.08788)). Automated post-hoc diagnosis finds the decisive failing step only 14.2% of the time ([Who&When](https://arxiv.org/abs/2505.00212)). Checks grounded in something external have the strongest measured effect: executable feedback added 4.2 and 5.4 points for MetaGPT, and a high-level verification step lifted ChatDev from 25.0 to 40.6 ([MetaGPT](https://arxiv.org/html/2308.00352v7); [MAST v2](https://arxiv.org/html/2503.13657v2)). No peer-reviewed study reports both catch rate and false-positive rate for an independent reviewer on realistic work with 2026 models.

## Records, references and isolated workspaces beat shared mutable state

The comparison below ranks each candidate structure by its evidence for teams of LLM workers. The classic distributed-systems statements in this section (MapReduce semantics, snapshot isolation, sagas, leases) are standard results cited from their canonical sources in the notes and were not re-read; the LLM-agent evidence is marked by type.

| Structure | What it buys | Evidence with LLM agents | Verdict |
|---|---|---|---|
| Task list with ids and dependency placeholders (`$1`, `<resource>-id`), scheduled and substituted by code | Explicit edges; model plans once, code dispatches; independent nodes run together | Measured: 1.8x to 3.7x speedup, planner at fault in only 8% of failures ([LLMCompiler](https://arxiv.org/html/2312.04511v3)); same convention since [HuggingGPT](https://arxiv.org/html/2303.17580) | Adopt. Risk is a stale up-front plan; no source measures replan frequency |
| Typed per-unit result record (evidence, rationale, answer or explicit "no information", support level), schema-validated with retry | Comparable, mergeable outputs; a refusal value; a place for provenance | Measured ablation worth 15 to 35 points ([LLM×MapReduce](https://arxiv.org/html/2410.09342v1)); validation with retry is practice in [LCM](https://arxiv.org/html/2605.04050v1) and DocETL, with no ablation. One 7B-model preprint found JSON between agents cut accuracy from 75.0% to 45.0% ([arXiv 2607.26922](https://arxiv.org/abs/2607.26922), abstract only) | Adopt, with validation at the boundary and capable models |
| Shared state with reducers (LangGraph channels) | A defined rule for concurrent same-key writes; an error when no rule is declared ([LangGraph errors](https://docs.langchain.com/oss/python/langgraph/errors/INVALID_CONCURRENT_GRAPH_UPDATE)) | Documented semantics only; no measurements | Use the idea in its simplest form: partition keys so each unit writes only its own, and reduce with associative code |
| Open blackboard, all agents read and write | Decoupling; opportunistic contribution | Measured small gain (81.68 against 80.09 for chain-of-thought) with extra resolver and cleaner roles ([LbMAS](https://arxiv.org/html/2507.01701v1)). The strongest blackboard result isolates helpers from each other and has one reader ([data discovery](https://arxiv.org/html/2510.01285v2)), which makes it hub and spoke with self-selection | Avoid the open form. Shared mutable coordination state failed at Cursor |
| Append-only event log, checkpoints, recorded step results | Resume, replay, audit; the recorded output is the truth, so a non-deterministic step is never regenerated ([Temporal docs](https://docs.temporal.io/workflows)) | Documented mechanism in LangGraph, MAF, Temporal, Restate; no measured recovery or duplicate-effect rates. | Locks held by agents | Exclusive access | Measured failure: held too long, never released, lost on crash; 20 agents at the throughput of 1 to 3 ([Cursor](https://cursor.com/blog/scaling-agents)) | Do not build |
| Claims and leases enforced by a tool or store | Prevents duplicate work | Small-scale success with claim files and git push as arbiter across 16 agents ([Anthropic C compiler](https://www.anthropic.com/engineering/building-c-compiler)); a synthetic study cut duplicate work from 78% to 0% with locks plus shared completion state, seen only through a secondary summary ([Vaughan](https://codex.danielvaughan.com/2026/06/20/before-the-pull-request-multi-agent-coordination-codex-cli-grite-duplicate-work-prevention/)) | Needed only when workers pick their own tasks. A planner that assigns work removes the need |
| Optimistic version check at commit | No waiting; a crash costs others nothing | Field report: better than locks, did not remove confusion, and agents without ownership drifted to small safe changes ([Cursor](https://cursor.com/blog/scaling-agents)) | Good as a commit-time validation, not as a coordination scheme |
| Isolated workspace per writer (worktree, clone, VM), merge or review at commit | Writers never collide physically; conflicts surface and stop | Best field support: every major coding product uses it ([Claude Code worktrees](https://code.claude.com/docs/en/worktrees); [Codex worktrees](https://learn.chatgpt.com/docs/environments/git-worktrees); [Cursor](https://cursor.com/blog/self-driving-codebases)). No measured conflict rates published. Isolation does not prevent semantic conflicts or duplicate work | Adopt; add a check after merge |
| CRDTs | Byte-level convergence without coordination | Measured: 100% convergence, zero merge failures, 5% to 10% semantic conflicts, from +21.1% to -39.4% speed ([CodeCRDT](https://arxiv.org/abs/2510.18893), single-author preprint). AgentRoom concludes "Coordination, not parallelism or CRDT-merge, is the key design choice" ([AgentRoom](https://arxiv.org/abs/2608.23740)) | Do not build unless humans and agents co-edit one text in real time |
| Actor mailboxes | Private state, async messages, supervision | Adopted by AutoGen Core with no scaling data; its successor moved to supersteps for checkpointable boundaries. Claude Code agent teams use JSON mailboxes and remain experimental, with lagging task status and early completion ([agent teams docs](https://code.claude.com/docs/en/agent-teams)) | Take the supervisor (deadlines, restart limits) as code; skip peer mailboxes |
| Handoff document, one-way, upward | Carries what a schema misses: concerns, deviations, findings | Field practice in Cursor's final design; Cognition's manager pattern fails without it ("cross-agent communication doesn't happen by default") | Adopt as a free-text field inside the typed record, stored verbatim |

The systems with the strongest long-input results all moved the combine step away from an unconstrained model call. LCM deliberately did not build an `llm_reduce` and recommends deterministic code; LOTUS requires an associative, commutative aggregation; LLM×MapReduce folds fixed-shape records ([LCM](https://arxiv.org/html/2605.04050v1); [LOTUS](https://arxiv.org/html/2407.11418v3)). The reason is the same one MapReduce documented for non-deterministic operators: each unit's output corresponds to some valid run, but two units may have worked under mutually inconsistent assumptions, so the reduce step has to check cross-unit consistency. Free-text summarize-the-summaries is neither associative nor commutative, so order and grouping change the result.

Two transfers from classic concurrency deserve emphasis because they are cheap. Re-running an LLM unit produces a different output, so recovery must reuse the recorded result, and commits should be idempotent and keyed by unit id so a retry or duplicate cannot land twice. And an isolated snapshot per writer has a known blind spot, write skew: two units make individually valid changes that jointly break an invariant. A text merge does not see it. Tests or a reviewer after the merge must. This is carried over from database theory; no agent study measures it by that name, and CodeCRDT's 5% to 10% semantic conflict rate is the nearest evidence.

## Sequential, coupled or already-solvable work should stay with one agent

Parallel agents are not worth building or invoking in five situations, each with evidence. When steps depend on each other in sequence, every multi-agent topology lost; on SWE-bench Verified all four topologies scored below the single agent's 0.522, by 2.1% to 14.9% ([Kim et al. v3](https://arxiv.org/html/2512.08296v3)). When the single agent already succeeds often, coordination adds cost and removes accuracy. When the whole input fits the window comfortably, decomposition loses or ties: LCM trails at 8K and 16K tokens and RLM is slightly worse than the base model on short inputs ([LCM](https://arxiv.org/html/2605.04050v1); [RLM](https://arxiv.org/html/2512.24601v1)). ContextlessAI's own probes say the same thing from the other side: the whole history, when it fits, put all 30 sources in the packet against 29 for selection. When units must agree on an interface or style that is not yet written down, parallel writers make conflicting implicit decisions; Anthropic states that most coding tasks have fewer parallelizable parts than research ([Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system)). And when the task's value does not cover 2x to 15x the tokens, the economics fail regardless of quality.

One field report shows the boundary clearly. Sixteen agents built a 100,000-line C compiler while there were many independent failing tests; on a single monolithic task "every agent would hit the same bug, fix that bug, and then overwrite each other's changes". Parallelism returned only when a known-good oracle let each agent work on a different subset of files ([Anthropic C compiler](https://www.anthropic.com/engineering/building-c-compiler)). The useful test before fanning out is therefore three questions: can each unit be specified in a self-contained brief, verified on its own, and merged without another unit's decisions? If any answer is no, either write the shared decision down first or keep one writer. For human-supervised coding, review throughput is the binding limit; one practitioner caps at four concurrent sessions per repository for that reason (anecdote) ([Context Studios](https://www.contextstudios.ai/blog/run-10-claude-code-agents-review-is-your-real-bottleneck)).

## ContextlessAI should type its unit results and reduce in code

The existing design already matches the best-supported pattern in most respects. Control flow is code over schema-validated handoffs. Each unit gets a fresh packet built by code, which is the self-contained brief. The vault is an immutable store addressed by stable ids, which is the "external storage plus lightweight references" that Anthropic adopted to avoid the telephone effect, with the added property that references resolve to verbatim text. Coder units get one worktree and branch each, the engine diffs, enforces the allowlist, commits once and runs verify, and nothing merges automatically: that is isolated workspace with validation at commit, with the agent unable to corrupt the claim discipline that broke Cursor's lock file. One process writes a workspace at a time, so there are no concurrent writers to the vault and no need for vault-level concurrency control. The reviewer runs on a provider that wrote none of the answer and must quote what it objects to, which is a grounding rule of the kind that separates useful verification from the 22.5% to 70.4% false-positive regime. The gaps are in what units return, how the plan expresses dependencies, how outputs are combined, and what is measured.

### Priorities

| Priority | Change | Basis |
|---|---|---|
| 1 | A typed unit result record with atom-level evidence, validated and quote-checked by the engine | Measured ablation (LLM×MapReduce); practice (LCM, DocETL) |
| 2 | Reduce in code before the assembler writes; assembler must account for every unit claim | Measured join failures (LLMCompiler 28%, RLM); design choice of LCM and LOTUS |
| 3 | Plan as a validated task list with ids, dependency placeholders and a shared-decisions block; engine gate that refuses plans it cannot justify | Measured (LLMCompiler, Skeleton-of-Thought router); practice (LCM delegation guard); argument (Cognition) |
| 4 | Measure plan against single call on the same messages, plus join and review quality | No local evidence exists yet that plans help; the external mean is -3.5% |
| 5 | Unit-level recorded results for resume, idempotent coder commits, base sha in the record | Documented mechanism (Temporal, LangGraph); carried over from MapReduce |
| 6 | Deterministic checks ahead of the reviewer; an optional scratch integration check across coder branches | Measured (rules AUROC 0.95+, executable feedback); write skew is an argument, not a measurement |
| 7 | Per-unit deadlines, restart limits, and an optional duplicate of a straggler on another lane | Carried over from supervision and MapReduce backup tasks; unmeasured for LLM work |

### What units should return

Every unit, whatever its role, should return one record of fixed shape, stored verbatim under `artifacts/<run-id>/` and indexed in `state.db`, with the fields below. The record replaces free-text unit output as the thing the assembler and reviewer consume.

| Field | Content | Engine check |
|---|---|---|
| `unit_id`, `plan_id`, `depends_on` | Identity and the edges the plan declared | Must match the plan |
| `status` | `completed`, `no_information`, `partial`, `blocked`, `needs_recall` | `no_information` records are dropped from the reduce, never passed to the assembler as content |
| `claims[]` | Each claim: text, `evidence` as atom ids (`tNNNNNN#aK`, ranges allowed) or artifact paths with sha, a verbatim `quote`, and `support`: `quoted`, `inferred` or `unsupported` | Every id must exist; every quote must occur in the cited atom, the same check the indexer's quotes already get. A claim marked `quoted` whose quote fails is downgraded or the unit is retried with the validation error |
| `assumptions[]` | Decisions the unit made that another unit could have made differently (an interface, a name, a unit of measure, a reading of the request) | Compared across units in the reduce |
| `open_questions[]`, `conflicts[]` | What the unit could not settle; evidence it saw that disagrees with its own answer or the brief | Surfaced to the assembler and the final report |
| `artifacts[]` | Path and sha of files produced; for coder units, branch, commit, base sha, files changed, verify command and result | Already produced by the repository lane; add the base sha |
| `notes` | Free text: concerns, deviations from the brief, findings a sibling should know | Stored verbatim, never summarized |

Three choices in this record follow the evidence directly. The explicit `no_information` status is the measured remedy for units that fabricate from irrelevant input. The `support` field is a three-level class tied to a checkable quote, not a numeric confidence: in the LLM×MapReduce ablation the structured record carried almost all the gain and calibration only 2 to 5 points, and that paper gives no rule for how scores settle a conflict, so a number the engine cannot check is not worth asking for. The `assumptions` and `notes` fields are the handoff document, the one place where Cursor's and Cognition's field experience says a schema alone falls short. Atom ids are what make this cheap: because atoms are stable addresses into immutable turns, evidence can be passed by reference and verified by code, which no surveyed system can do as directly. The 7B-model result against JSON handoffs is a warning to validate at the boundary and retry with the error, as LCM does, and to keep the record small.

For chunk units, the case where the focus itself is too large and principle 2 splits it, this record is the LLM×MapReduce map output almost field for field, and that is the case with the strongest external evidence for decomposition.

### How the plan should express work

The `plan` handoff should carry a task list in which each unit has an id, a role, a brief, an output expectation, and `depends_on` ids, and in which a dependent unit refers to an earlier result by placeholder. The engine, not a model, resolves a placeholder by pinning the upstream unit's result record verbatim into the dependent unit's packet at tier 0, and runs units in waves: everything whose dependencies are met runs together, then the next wave. A simple barrier per wave is adequate at this scale; its cost is waiting for the slowest unit, which should be measured before anything more elaborate is considered. The plan should also carry a `shared_decisions` block (names, interfaces, formats, scope boundaries) that the engine copies into every unit's packet, because copying the original task to each unit does not prevent divergent implicit decisions.

The engine should refuse or downgrade plans by rule. A plan with one unit is a normal call. A plan whose units form a pure chain is a sequential task and should run as one responder call with continuations, since that is where every measured topology lost. Coder units naming the same repository must have disjoint path allowlists unless one depends on the other. Fan-out should be capped at about five units per wave, the convergent rule of thumb, which is unproven as an optimum but consistent with the near-quadratic growth in coordination turns. Following LCM's delegation guard, the plan should state in one line per unit why the unit is independently verifiable; a plan that cannot say so is rejected back to a single call. The current flow, in which the responder proposes a plan only when it judges one necessary, is already a cascade of the kind that beat both pure strategies; the gate makes it enforceable.

### How outputs should be combined and checked

The combine step should be two stages, with code first. The engine drops `no_information` records, verifies evidence, unions the surviving claims, merges claims that cite the same atoms, lists every pair of units whose `assumptions` or claims cite the same atom or name the same key with different values, and collects `conflicts` and `open_questions`. That reduce is associative and order-independent, so retrying one unit changes only that unit's contribution. The assembler then receives the unit records verbatim (not each unit's prose restated by another model, and not the transcript again), the engine's conflict list, and the shared decisions, and writes one answer under an output contract: each substantive statement cites a unit claim id or an atom id, and the handoff lists any unit claim it left out with a reason. The engine checks that every cited id exists and that every surviving claim is either cited or listed as omitted. This makes the two join failures seen in the literature, discarding a correct unit result and asserting agreement that the units do not support, visible to code. When units disagree on a fact, the assembler should not pick silently. The measured remedy is to rerun the disagreeing units with each other's evidence pinned, which is how LongAgent's members corrected themselves, capped at one round; if disagreement survives, the answer states both positions with their evidence. If unit records exceed the assembler's plan cap, the existing sizing rules apply: larger profile first, then a hierarchical reduce over records of the same shape, never a rewrite of a record into a shorter one.

Checking should be ordered from cheapest and most reliable to least. Deterministic checks run first: schema, evidence ids and quotes, citation coverage, allowlist, and the verify command for coder units, which is the executable-feedback check with the best measured effect. The cross-provider reviewer runs second, on the assembled answer plus the unit records, with the existing rule that a problem must quote the answer or name something missing; the one-round limit matches the finding that debate gains flatten after the second round and that aggressive judges flip correct answers. The writer filtering the reviewer's surviving problems mirrors the Devin Review arrangement. Two additions are worth making: give the reviewer the engine's conflict list so it checks the join specifically, and fix the documented gap that a reviewer cannot recall, since a reviewer limited to what the writer recalled inherits the writer's blind spots. Whether the different-provider rule itself adds catch rate is unmeasured anywhere; keep it, and measure it.

For plans with several coder units, the engine can add one optional step after all units pass verify: create a scratch branch from the shared base, merge the unit branches in plan order, run the verify command once, and report the result, deleting the scratch branch afterward. Nothing lands; the user still decides. This catches textual conflicts and write skew between units that each passed alone, and it is a merge queue of length one without the bottleneck that sank Cursor's integrator. It rests on argument, not on a measured conflict rate, so build it only after the measurements below show multi-coder plans are used and that their branches conflict.

For recovery, the unit record is the unit of durability. A plan interrupted mid-wave should resume by reusing every unit whose record is stored and rerunning only the rest, as LangGraph does with completed nodes in a failed superstep; a rerun unit's record supersedes nothing that an assembler already consumed, because the assembler runs only after the wave completes. Coder commits should be keyed by unit id so a retried unit cannot commit twice on its branch, and the record should carry the repository base sha so the final report can say when the base has moved since the unit branched.

### What to measure

The first measurement decides whether the plan path deserves further work: run the same sample of messages once as a single responder call and once through a plan, and score the answers blind, recording billed cost and wall time from `usage.json`. Include a budget-matched arm where the single call gets a larger window or higher effort, because the published record says unmatched comparisons flatter multi-agent systems. Report by request class, since the external spread runs from +80.8% to -70%.

Second, instrument the join. Per plan, record the share of unit claims that failed the quote check, the `no_information` rate, the share of surviving claims the assembler cited, the share it omitted with and without a stated reason, citations that do not resolve, and the number of cross-unit conflicts found by code against the number mentioned in the final answer. The last ratio is a local estimate of the quantity no paper reports: how often a merger hides a disagreement.

Third, measure the reviewer the way the probes measure retrieval, without trusting it. Seed known errors into otherwise good assembled answers (a changed value, a dropped unit claim, a claim with no evidence) and measure catch rate; run the reviewer on clean answers and measure the rate of problems that survive the quote rule, which is its false-positive rate. Compare a same-provider reviewer on the same items. Thirty items give the same 3.3-point resolution the probe sets have, so treat small differences as noise.

Fourth, measure coordination cost directly: wall time split into planning, the wait for the slowest unit in each wave, assembly and review; total tokens against the single-call arm; and throughput at 1, 2, 3 and 5 units on a fixed class of task, which is enough to fit the contention and coherency terms of the Universal Scalability Law and see where adding units stops paying. Also track recall rounds per unit as the fault rate of unit packets, verify pass rate per coder unit, scratch-merge conflict rate, and how often two units cite the same atoms for the same claim, a cheap proxy for duplicated work.

### What not to build

Do not give units a shared writable surface: no blackboard, no shared scratch file, no unit-to-unit mailbox or chat. The single-writer rule for the vault is an asset, and the field evidence against shared mutable coordination state is the most consistent finding in this survey. Do not build agent-held locks, leases with fencing tokens or a claim protocol; the planner assigns units, the engine owns commits, and one process writes, so there is nothing for a claim to protect. Do not adopt CRDTs; git branches with a conflict that stops are the better fit for code, and convergence without validation is measured to be wrong 5% to 10% of the time. Do not add debate rounds, voting among units or numeric confidence scores as a merge rule. Do not build an LLM integrator that merges coder branches on its own, a merge queue beyond the scratch check, or automatic merging of any kind. Do not let any model summarize a unit's output for another model; pass the record verbatim or by id, which is the engine's founding principle applied to unit outputs. Do not raise fan-out beyond a handful of units or add recursive sub-planning until the plan-against-single measurement shows a gain at the current size. And do not adopt a superstep framework, an actor runtime, A2A or topology search: the engine already has explicit control flow in code, the protocols standardize envelopes without evidence or provenance fields, and searched topologies differ from each other mainly in cost.

## Conclusion

The research record reframes the question. The choice of topology or coordination substrate explains little; what is passed between units and who is allowed to write explains most of what works. Systems that pass checkable artifacts by reference, keep one writer per surface, and put scheduling and reduction in code are the ones with measurements behind them, and the systems that tried to make agents share and negotiate state retreated from it. Most of the celebrated multi-agent gains turn out to be more tokens in more context windows, which a single well-budgeted call often matches, so the honest default is one agent, with fan-out reserved for inputs that exceed the window, independent lookups, and separable writes.

ContextlessAI starts from an unusual position: its atoms give every unit a way to prove what it relied on, and its engine can verify that proof without a model. No surveyed system combines verbatim evidence addressing with deterministic packet building. That makes the cheapest high-value step a schema, not an architecture: a unit result record whose claims point at atoms. It also means the system can measure things the literature cannot yet answer, including how often an assembler hides a conflict and whether a different-provider reviewer catches more than a same-provider one. Those two numbers, measured locally, would be worth more to its design than any further borrowing from frameworks.
